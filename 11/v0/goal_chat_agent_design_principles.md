# Goal Chat Agent 设计总则

> 版本：v0.1  
> 用途：作为微信聊天 agent 底层架构与后续状态机设计的总原则。  
> 范围：第 0 层架构原则、状态机边界、工具调用原则、历史写入原则、扩展接口原则。  
> 不包含：具体代码实现、具体 prompt 文案、主动消息细节、情绪模型细节。

---

## 1. 系统定位

Goal Chat Agent 不是普通网页聊天机器人，而是一个模拟真人微信聊天的后端 agent。

系统目标是：

1. 接收微信消息。
2. 构建模型需要的上下文。
3. 让模型判断要不要调用工具。
4. 让模型最终明确选择：回复，或不回复。
5. 如果回复，必须通过真实微信发送链路发出去。
6. 如果不回复，必须通过明确的跳过回复出口结束。
7. 所有可见微信输出都必须经过统一状态机、输出保护和发送层。

一句话原则：

> 模型可以决定怎么回，但不能绕过工具直接把普通文本变成微信消息。

---

## 2. 第 0 层架构目标

第 0 层状态机图（Level-0 State Machine Diagram）只描述一轮对话的总体生命周期。

它回答这些问题：

- 一轮对话从哪里进入？
- 上下文在哪里构建？
- 模型在哪里调用？
- 工具在哪里执行？
- 微信在哪里发送？
- 失败在哪里兜底？
- 历史在哪里写入？
- 最终有哪些结束状态？

它不回答这些问题：

- 某个函数怎么写？
- 某个 prompt 怎么措辞？
- 主动消息什么时候触发？
- 情绪值怎么计算？
- 每个工具的具体业务参数是什么？

第 0 层只定骨架，不塞未来功能细节。

---

## 3. 核心术语

| 字段 / 名词 | 含义 |
|---|---|
| `TURN`（对话回合） | 系统处理一次输入并产出一个明确结果的完整过程。 |
| `TURN_SOURCE`（回合来源） | 本轮由什么触发，例如用户消息、主动消息触发。 |
| `USER_MESSAGE`（用户消息） | 用户从微信发来的真实消息。 |
| `PROACTIVE_TRIGGER`（主动消息触发） | 系统未来主动开口的触发来源。当前只预留接口，不展开实现。 |
| `BUILD_CONTEXT`（构建上下文） | 把人设、最近聊天记录、摘要、工具结果等整理成模型输入。 |
| `CALL_LLM`（调用模型） | 请求大模型生成下一步动作。 |
| `assistant.content`（模型普通文本输出） | 模型直接输出在内容字段里的普通文本。新架构中它不能直接发微信。 |
| `tool_calls`（工具调用字段） | 模型通过 API 结构化字段声明要调用哪个工具以及参数。 |
| `native tool calls`（原生工具调用） | 使用模型 API 的工具调用能力，而不是让模型在普通文本里写 JSON。 |
| `FACT_TOOL`（事实工具 / 信息工具） | 查信息用的工具，例如时间、天气。结果返回给模型继续判断。 |
| `TERMINAL_TOOL`（终态工具） | 一旦执行，本轮就应该结束的工具，例如发送微信、跳过回复。 |
| `STATE_TOOL`（状态工具） | 修改内部状态的工具，例如未来可能更新 persona、偏好、情绪状态。当前只预留分类。 |
| `send_wechat_messages`（发送微信消息） | 真实副作用工具，用于把可见消息发到微信端。 |
| `skip_reply`（跳过回复） | 终态工具，用于明确表示本轮不回复。 |
| `PROTOCOL_RETRY`（协议重试） | 模型没有按协议调用终态工具时，系统提醒模型重新按协议输出。 |
| `SEND_RETRY`（发送重试） | 微信发送失败后，只重试未送达的原消息，不重新调用模型。 |
| `fallback`（兜底） | 正常流程失败时的备用处理。 |
| `hard fallback`（硬兜底） | 不使用模型原文，只使用系统固定文案保底。 |
| `LLM error`（模型调用报错） | 调用模型 API 失败，例如超时、网络异常、接口异常。 |
| `empty response`（空响应） | 模型成功返回，但既没有工具调用，也没有有效内容。 |
| `_send_fallback_text`（发送兜底文本函数） | 旧代码中的兜底发送函数。新架构中应移除其混合职责，不允许用模型普通文本兜底发送。 |
| `guard`（输出保护） | 发送前检查消息是否泄露协议、工具名、JSON、内部字段等。 |
| `POST_TURN_HOOKS`（回合结束后钩子） | 回合结束后的统一后处理区域，例如写历史、写日志、更新摘要、更新情绪。 |
| `END_SENT`（正常发送结束） | 模型按协议调用发送工具，微信发送成功。 |
| `END_SKIPPED`（跳过结束） | 模型按协议调用跳过工具，本轮不回复。 |
| `END_FAILED`（失败结束） | 本轮未完成正常发送，也未成功兜底。 |
| `END_FALLBACK_SENT`（兜底已发送结束） | 系统发送了固定兜底文案，但不算模型正常回复成功。 |

## 4. 最重要的架构原则

### 4.1 所有回合必须有明确终态

一轮对话不能模糊结束。

合法终态包括：

- `END_SENT`（正常发送结束）
- `END_SKIPPED`（跳过结束）
- `END_FALLBACK_SENT`（兜底已发送结束）
- `END_FAILED`（失败结束）

禁止出现：

- 模型输出了普通文本，但系统不知道发没发。
- 工具执行了一半，但没有终态记录。
- 发送失败了，但历史里像成功一样写入。
- 跳过回复是靠空消息列表事后猜出来的。

---

### 4.2 模型每轮必须最终调用终态工具

当前版本中，模型最终必须调用以下两类终态工具之一：

1. `send_wechat_messages`（发送微信消息）
2. `skip_reply`（跳过回复）

如果模型只输出 `assistant.content`（模型普通文本输出），但没有 `tool_calls`（工具调用字段），系统不能把该文本发到微信。

正确处理方式是：

```text
assistant.content without terminal tool
→ PROTOCOL_RETRY（协议重试）
→ 再次 CALL_LLM（调用模型）
→ 仍失败则 HARD_FALLBACK（硬兜底）或 END_FAILED（失败结束）
```

---

### 4.3 不兼容旧 JSON actions

新架构不再承认 `assistant.content`（模型普通文本输出）里的 JSON actions 是合法动作。

旧方式：

```json
{
  "actions": [
    {
      "type": "tool",
      "name": "wechat_reply",
      "args": {
        "text": "我在"
      }
    }
  ]
}
```

新架构中，这只是模型普通文本，不是合法工具调用。

新方式必须使用 API 的 `tool_calls`（工具调用字段）：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "type": "function",
      "function": {
        "name": "send_wechat_messages",
        "arguments": "{\"messages\":[{\"text\":\"我在\",\"delay\":0}]}"
      }
    }
  ]
}
```

注意：这里底层仍然有 JSON，但 JSON 位于 API 的结构化工具调用参数里，不是模型聊天文本里。

一句话区分：

> 旧协议是让模型在聊天框里手写 JSON；新协议是让模型通过 API 的工具调用字段点按钮、填表单。

---

### 4.4 事实工具只提供信息，不生成回复

`get_time`（获取时间）和 `get_weather`（获取天气）这类工具属于 `FACT_TOOL`（事实工具 / 信息工具）。

它们的职责是：

1. 接收模型传来的参数。
2. 查询事实结果。
3. 把结果返回给模型。
4. 让模型结合上下文决定如何回复。

它们不能直接生成微信回复，也不能直接发送微信。

正确流程：

```text
用户问天气
→ 模型调用 get_weather（获取天气）
→ 系统返回天气结果给模型
→ 模型调用 send_wechat_messages（发送微信消息）
→ 系统发送微信
```

---

### 4.5 真实副作用工具不能把执行结果喂回模型

`send_wechat_messages`（发送微信消息）是真实副作用工具。

它执行成功后，本轮应该直接进入 `END_SENT`（正常发送结束），不能把“已发送 2/2 条微信消息”之类的结果作为 tool result 再塞回模型。

原因：

- 发送已经发生，再让模型看到发送结果没有意义。
- 可能污染下一轮上下文。
- 可能让模型围绕“已发送”继续说话。
- 会模糊事实工具和终态工具的边界。

规则：

```text
FACT_TOOL（事实工具）执行结果 → 可以返回给模型
TERMINAL_TOOL（终态工具）执行结果 → 不返回给模型，直接进入终态
```

---

### 4.6 微信发送失败后不重新调用模型

如果 `send_wechat_messages`（发送微信消息）失败，系统只能进入 `SEND_RETRY`（发送重试）。

规则：

- 总计最多尝试 3 轮：初始发送 + 2 次重试。
- 已经送达的消息必须标记为成功。
- 已经成功的消息绝对不能重发。
- 只重试未送达的消息。
- 重试期间不能重新调用模型。
- 超过重试次数仍失败，进入 `END_FAILED`（失败结束）。
- 失败详情写入开发日志，不写入助手成功历史。

不建议“全部删除让模型重新生成”。

理由：发送失败发生在副作用阶段，不是生成阶段。重新调用模型可能改变消息条数、语义、顺序，反而更容易产生重复发送和上下文错乱。

---

### 4.7 硬兜底不算正常回复成功

`hard fallback`（硬兜底）是系统保命，不是模型正常完成对话。

如果系统发出固定兜底文案，例如：

```text
我刚刚卡了一下 重新说
```

则终态应该是：

```text
END_FALLBACK_SENT（兜底已发送结束）
```

而不是：

```text
END_SENT（正常发送结束）
```

这样日志和质量统计才不会骗人。

---

### 4.8 所有可见微信输出必须经过 guard

任何最终会发到微信的文本，都必须经过 `guard`（输出保护）。

包括：

- 模型通过 `send_wechat_messages`（发送微信消息）提交的文本。
- 系统固定 `hard fallback`（硬兜底）文案。
- 未来主动消息。
- 未来其他可见输出。

禁止绕过 guard 直接 append 到发送列表。

---

## 5. 历史写入原则

### 5.1 历史不是日志

本系统的历史记录不是给人看的。

人类已经能在微信端看到聊天记录。

历史记录的唯一目的：

> 让模型知道刚才聊了什么。

因此要区分：

| 类型 | 服务对象 | 内容 |
|---|---|---|
| 历史 | 模型 | 最近对话、摘要、上下文信息 |
| 日志 | 开发者 | 状态、错误、失败原因、调试信息 |

不要把开发日志塞给模型。

---

### 5.2 三层历史结构

#### 第一层：最近原始聊天记录

保留最近约 20 轮原始聊天记录。

这里的“原始”指模型能看懂的真实对话，不是内部 JSON actions。

推荐格式：

```text
[user] 你在干嘛
[assistant] 刚弄完一点东西，你呢
[user] 有点累
[assistant] 那先别硬撑，先休息十分钟
```

主动消息需要明确标记：

```text
[assistant:proactive] 你今天计划推进得怎么样了？
[user] 刚开始
```

---

#### 第二层：最近谈话小总结

对最近若干轮对话做滚动压缩。

用途：降低上下文长度，同时保留近期主题。

示例：

```text
最近聊天摘要：
用户正在设计微信聊天 agent 的底层状态机，重点关注 native tool calls、send_wechat_messages、skip_reply、fallback、历史写入和未来扩展口。
```

---

#### 第三层：每日总结

每天结束后生成当天总结。

第二天对话时注入昨日总结。

用途：让模型知道较长期的上下文，但不引入长期记忆系统。

---

### 5.3 不同终态下的历史写入

| 终态 | 写 user 历史 | 写 assistant 历史 | 说明 |
|---|---:|---:|---|
| `END_SENT`（正常发送结束） | 是 | 是 | 写真实成功发出的文本。 |
| `END_SKIPPED`（跳过结束） | 是 | 否 | 用户说过什么要保留，但 bot 没有回复。 |
| `END_FALLBACK_SENT`（兜底已发送结束） | 是 | 可选 | 若写入，必须标记为 fallback，避免模型误以为这是正常风格。 |
| `END_FAILED`（失败结束） | 是 | 否 | 不写助手成功回复。失败详情写日志。 |
| 部分发送成功后失败 | 是 | 只写成功送达部分，或标记 partial | 不能把未送达内容写成已回复。 |

---

## 6. 工具分类原则

所有工具必须先分类，再接入状态机。

| 分类 | 含义 | 当前工具 | 执行后流向 |
|---|---|---|---|
| `FACT_TOOL`（事实工具 / 信息工具） | 查事实、查信息 | `get_time`、`get_weather` | 工具结果返回模型，继续 `CALL_LLM`。 |
| `TERMINAL_TOOL`（终态工具） | 结束本轮 | `send_wechat_messages`、`skip_reply` | 执行后进入终态。 |
| `STATE_TOOL`（状态工具） | 修改内部状态 | 未来可能的 persona、偏好、情绪工具 | 视工具定义决定返回模型或结束。 |

新增工具必须声明：

1. 工具名。
2. 参数 schema。
3. 工具分类。
4. 是否允许模型调用。
5. 是否有真实副作用。
6. 执行后是否回到模型。
7. 是否会产生可见微信输出。

禁止新增工具时直接在主循环里临时写 if/else。

---

## 7. 未来功能扩展原则

### 7.1 主动消息

主动消息不应该拥有独立发送链路。

未来正确接入方式：

```text
PROACTIVE_TRIGGER（主动消息触发）
→ CREATE_TURN（创建回合）
→ BUILD_CONTEXT（构建上下文）
→ CALL_LLM（调用模型）
→ 模型调用 send_wechat_messages 或 skip_reply
```

主动消息只是 `TURN_SOURCE`（回合来源）不同，不应该绕过模型、guard、发送层和历史层。

---

### 7.2 情绪板块

情绪板块不进入第 0 层主干。

它应该挂在两个位置：

1. `BUILD_CONTEXT`（构建上下文）：把当前情绪状态作为上下文提供给模型。
2. `POST_TURN_HOOKS`（回合结束后钩子）：根据本轮对话更新情绪状态。

情绪模块不能直接生成微信回复，也不能直接发送微信。

---

### 7.3 新工具

新增工具只应接入 `TOOL_CLASSIFICATION`（工具分类）和 `HANDLE_TOOL_CALLS`（处理工具调用）。

不能让每个新工具污染第 0 层主干。

---

## 8. 第 0 层状态机必须保留的扩展口

| 扩展口 | 中文含义 | 作用 |
|---|---|---|
| `TURN_SOURCE` | 回合来源 | 支持用户消息、主动消息等不同入口。 |
| `CONTEXT_COMPONENTS` | 上下文组件 | 支持最近历史、小总结、每日总结、情绪状态、人设等。 |
| `TOOL_CLASSIFICATION` | 工具分类 | 支持未来新增工具，不破坏主流程。 |
| `POST_TURN_HOOKS` | 回合结束后钩子 | 支持历史写入、摘要更新、情绪更新、日志记录。 |
| `POLICY_LAYER` | 策略层 | 支持未来回复策略、主动消息策略、情绪策略。 |

---

## 9. 明确禁止事项

1. 禁止把 `assistant.content`（模型普通文本输出）直接发到微信。
2. 禁止兼容旧 JSON actions 作为合法动作。
3. 禁止 `send_wechat_messages`（发送微信消息）成功后把 tool result 喂回模型。
4. 禁止微信发送失败后重新调用模型生成新消息。
5. 禁止已成功送达的消息被重发。
6. 禁止硬兜底使用模型原文。
7. 禁止硬兜底绕过 guard。
8. 禁止把日志当历史塞给模型。
9. 禁止主动消息绕过统一状态机直接发送。
10. 禁止新增工具时绕过工具分类。

---

## 10. 当前优先级

### P0：先保证主干正确

1. 新增 `skip_reply`（跳过回复）终态工具。
2. 将 `chat()` 改造成显式状态机。
3. 删除 `assistant.content` 直接发送路径。
4. 禁止 `send_wechat_messages` tool result 回灌模型。
5. 明确终态：`END_SENT`、`END_SKIPPED`、`END_FALLBACK_SENT`、`END_FAILED`。

### P1：再保证失败路径正确

1. 统一 `hard fallback`（硬兜底）文案。
2. 所有可见输出经过 guard。
3. 实现 `SEND_RETRY`（发送重试）：初始发送 + 2 次重试。
4. 历史写入按终态区分。

### P2：最后做清理和扩展

1. 删除旧 JSON actions 残留。
2. 清理旧工具和死代码。
3. 重写过时架构文档。
4. 接入摘要更新。
5. 预留主动消息和情绪板块，但不提前细化。

---

## 11. 总结

Goal Chat Agent 的底层架构必须围绕一个核心事实设计：

> 微信发送是真实副作用，不是模型文本输出。

因此，新架构的地基是：

```text
模型必须通过 native tool calls（原生工具调用）选择动作。
普通文本不是动作。
所有可见输出必须走统一发送链路。
所有回合必须有明确终态。
历史只服务模型理解上下文，日志才服务开发者排查问题。
```
