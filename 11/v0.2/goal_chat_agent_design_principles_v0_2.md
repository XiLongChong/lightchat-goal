# Goal Chat Agent 底层架构设计总则 v0.2

> 适用项目：Goal Chat Agent / 微信聊天 Agent  
> 文档定位：第 0 层架构约束与设计总则  
> 当前阶段：native tool calls（原生工具调用）架构迁移期  
> 核心目标：把“微信可见输出”从模型普通文本中彻底剥离，统一收敛到状态机、终态工具、输出保护、发送结果和历史/记忆后处理。

---

## 0. 本文档解决什么问题

本系统不是普通网页聊天机器人，而是一个模拟真人微信聊天的 Agent。

它的核心风险不是“模型不会说话”，而是：

1. 模型生成了内容，但没有真正发到微信端。
2. 模型普通文本被后端误当成微信回复直接发送。
3. `send_wechat_messages`（发送微信消息工具）的结果被喂回模型，污染上下文。
4. “不回复”不是显式决策，而是靠空消息列表事后猜测。
5. fallback（兜底）路径太多，部分绕过 guard（输出保护）。
6. 历史、日志、记忆混在一起，导致模型上下文污染。
7. 未来新增主动消息、情绪板块、记忆系统、新工具时，绕过主流程。

因此，本设计总则只做一件事：

> 规定所有回合必须怎样进入、怎样决策、怎样发送、怎样结束、怎样写历史和记忆。

---

## 1. 核心设计原则

### 1.1 所有微信可见输出必须走统一主链路

任何用户最终能在微信里看到的内容，都必须经过：

```text
模型终态工具
→ 输出保护
→ 微信发送
→ 发送结果终态
→ 历史 / 记忆 / 日志后处理
```

禁止任何模块直接绕过主链路发微信。

包括但不限于：

- 主动消息模块
- 情绪模块
- 记忆模块
- fallback（兜底）模块
- 预处理模块
- 未来新增工具

---

### 1.2 模型必须通过 terminal tool（终态工具）结束本轮

每一轮模型最终必须调用以下之一：

1. `send_wechat_messages`（发送微信消息）
2. `skip_reply`（跳过回复）

如果模型只输出 `assistant.content`（模型普通文本输出），但没有 `tool_calls`（工具调用字段），则视为协议违规，进入 `PROTOCOL_RETRY`（协议重试）。

禁止：

```text
模型输出普通文本
→ 后端把普通文本直接发微信
```

允许：

```text
模型调用 send_wechat_messages
→ 后端解析参数
→ 输出保护
→ 真实微信发送
```

---

### 1.3 不兼容旧 JSON actions

新架构不承认 `assistant.content`（模型普通文本输出）里的旧 JSON actions 为合法动作。

旧协议示例：

```json
{
  "actions": [
    {
      "type": "tool",
      "name": "wechat_reply",
      "args": {
        "text": "我在"
      }
    }
  ]
}
```

在新架构中，这只是普通文本，不是合法工具调用。

如果模型这样输出，状态机应判断为：

```text
没有 native tool calls（原生工具调用）
→ PROTOCOL_RETRY（协议重试）
```

禁止继续解析旧 JSON actions、兼容 `wechat_reply`、兼容旧 `skip`。

---

### 1.4 native tool calls（原生工具调用）才是动作入口

native tool calls（原生工具调用）是模型 API 返回的结构化工具调用字段，不是模型在聊天文本中手写 JSON。

大白话：

- 旧方式：让模型在聊天内容里写一张 JSON 表单，后端从文本里抠。
- 新方式：系统给模型几个工具按钮，模型通过 API 的工具调用字段选择按钮并填写参数。

后端只认：

```text
response.tool_calls
```

不认：

```text
response.content 里的 JSON
```

---

### 1.5 工具层不生成微信回复

`get_time`（获取时间）、`get_weather`（获取天气）、未来的搜索、日历、记忆读取等工具，只提供信息，不组织最终回复。

正确流程：

```text
用户问天气
→ 模型调用 get_weather
→ 系统返回天气结果给模型
→ 模型结合上下文组织回复
→ 模型调用 send_wechat_messages
→ 系统发送微信
```

禁止：

```text
天气工具查到结果
→ 天气工具自己生成一句回复
→ 直接发微信
```

---

### 1.6 hard fallback（硬兜底）不算正常回复成功

`hard fallback`（硬兜底）是系统保命，不是模型正常聊天。

比如：

```text
我刚刚卡了一下 重新说
```

它可以被发到微信，但终态不能记为普通 `END_SENT`（正常发送结束）。

应记为：

```text
END_FALLBACK_SENT（兜底已发送结束）
```

或发送失败时：

```text
END_FAILED（失败结束）
```

## 2. 英文字段与术语说明

| 字段 / 名词 | 中文含义 | 说明 |
|---|---|---|
| `fallback` | 兜底 | 正常流程失败时的备用路径 |
| `hard fallback` | 硬兜底 | 不使用模型原文，只使用系统固定文案 |
| `LLM error` | 模型调用报错 | 调用模型 API 失败、超时、网络异常等 |
| `empty response` | 空响应 | 模型返回成功，但没有内容也没有工具调用 |
| `assistant.content` | 模型普通文本输出 | 模型直接写出的自然语言内容，不是工具调用 |
| `tool_calls` | 工具调用字段 | 模型 API 返回的结构化工具调用列表 |
| `native tool calls` | 原生工具调用 | 模型通过 API 工具字段调用工具，而非在文本里写 JSON |
| `terminal tool` | 终态工具 | 一调用就应结束本轮的工具 |
| `fact tool` | 事实工具 / 信息工具 | 查事实、查资料的工具，结果回灌模型 |
| `state tool` | 状态工具 | 修改系统内部状态的工具，如记忆、标签、情绪状态 |
| `system hook` | 系统钩子 | 回合后系统自动执行的逻辑，不给模型直接调用 |
| `protocol retry` | 协议重试 | 模型没按工具协议输出时，系统提醒其重试 |
| `send retry` | 发送重试 | 微信发送失败后，只重试未送达消息 |
| `guard` | 输出保护 | 检查所有可见消息，防止协议泄露、非法内容、格式污染 |
| `turn` | 回合 | 一次用户消息或主动触发所形成的完整处理周期 |
| `context` | 上下文 | 塞给模型的所有可读信息 |
| `memory` | 记忆 | 跨回合保存的用户相关长期信息 |
| `history` | 历史 | 给模型看的最近聊天记录，不是开发日志 |
| `log` | 日志 | 给开发者排查问题看的系统记录 |
| `interrupt` | 中断 | 当前回合被新消息或更高优先级事件取消 |
| `partial sent` | 部分发送成功 | 批量消息中只有一部分成功送达 |

## 3. 工具分类规则

未来新增任何工具，必须先归类。禁止随便加工具后在主流程里临时写分支。

### 3.1 `FACT_TOOL`（事实工具）

作用：查询外部或内部事实信息。

例子：

- `get_time`（获取时间）
- `get_weather`（获取天气）
- `search_web`（联网搜索，未来）
- `read_calendar`（读取日历，未来）
- `retrieve_memory`（检索记忆，未来，可作为系统上下文读取，不一定暴露给模型）

流转规则：

```text
模型调用 FACT_TOOL
→ 执行工具
→ 工具结果作为 tool result 回灌模型
→ 回到 CALL_LLM
```

限制：

- 事实工具不能直接发微信。
- 事实工具不能直接写 assistant 历史。
- 事实工具不能决定本轮终态。

---

### 3.2 `TERMINAL_TOOL`（终态工具）

作用：结束当前回合。

当前必须有：

- `send_wechat_messages`（发送微信消息）
- `skip_reply`（跳过回复）

流转规则：

```text
模型调用 TERMINAL_TOOL
→ 执行终态动作
→ 进入明确终态
```

限制：

- 终态工具不能和其他工具混用。
- 同一轮不能同时调用多个终态工具。
- `send_wechat_messages` 成功执行后，结果不能回灌模型。
- `skip_reply` 必须是显式工具调用，不能用空消息列表猜测。

---

### 3.3 `STATE_TOOL`（状态工具）

作用：修改内部状态，但不直接结束回合。

未来可能包括：

- `propose_memory_update`（提出记忆更新）
- `update_user_tags`（更新用户标签）
- `update_emotion_state`（更新情绪状态）
- `record_preference`（记录偏好）

流转规则：

```text
模型调用 STATE_TOOL
→ 执行内部状态修改或提出修改
→ 回到 CALL_LLM
→ 继续要求模型调用终态工具
```

关键原则：

> 模型调用的工具，执行完必须有明确去向。不能出现“既不回模型，也不结束”的悬空状态。

建议：

第一版记忆系统不要直接开放 `write_memory`（写记忆）给模型。  
更稳的是开放 `propose_memory_update`（提出记忆更新），由系统审核后再写入。

---

### 3.4 `SYSTEM_HOOK`（系统钩子）

作用：系统在回合后自动执行，不由模型直接调用。

例子：

- `UPDATE_SUMMARY`（更新摘要）
- `UPDATE_MEMORY`（更新记忆）
- `UPDATE_EMOTION`（更新情绪）
- `WRITE_LOGS`（写开发日志）
- `QUALITY_METRICS`（质量统计）

流转规则：

```text
终态已确定
→ 执行 POST_TURN_HOOKS
→ 不能修改主流程终态
```

限制：

- 不能补发微信。
- 不能修改已经确定的发送结果。
- 不能把失败消息伪装成成功历史。
- 不能把未送达内容写入用户已看到的对话历史。

---

## 4. 并行工具调用规则

现代模型可能一次返回多个 `tool_calls`（工具调用）。第 0 层必须定义组合规则。

| 工具组合 | 是否允许 | 处理方式 |
|---|---:|---|
| 多个 `FACT_TOOL` | 允许 | 可并行执行，结果合并后回灌模型 |
| 一个 `TERMINAL_TOOL` | 允许 | 执行终态动作 |
| 多个 `TERMINAL_TOOL` | 禁止 | 协议违规，进入 `PROTOCOL_RETRY` |
| `TERMINAL_TOOL` + 任意其他工具 | 禁止 | 协议违规，进入 `PROTOCOL_RETRY` |
| 多个 `STATE_TOOL` | v1 建议串行 | 避免副作用顺序混乱 |
| `STATE_TOOL` + `FACT_TOOL` | 允许但谨慎 | 执行后统一回到 `CALL_LLM` |
| 非法工具 / 未注册工具 | 禁止 | `PROTOCOL_RETRY`，超限后硬兜底 |

---

## 5. 上下文分层与隔离规则

历史、记忆、日志不能混为一谈。

### 5.1 四类上下文

| 层级 | 中文含义 | 生命周期 | 是否持久化 | 给谁看 |
|---|---|---|---:|---|
| `TURN_SCRATCHPAD` | 本轮临时区 | 当前回合内 | 否 | 状态机 / 模型临时使用 |
| `RECENT_HISTORY` | 最近原始聊天记录 | 最近若干轮 | 是 | 模型 |
| `SUMMARY_CONTEXT` | 摘要上下文 | 中期 | 是 | 模型 |
| `LONG_TERM_MEMORY` | 长期记忆 | 长期 | 是 | 模型 |
| `DEV_LOG` | 开发日志 | 长期或按策略轮转 | 是 | 开发者 |

---

### 5.2 模型历史的唯一目的

模型历史不是给人类看的。人类在微信端天然能看到聊天记录。

模型历史唯一目的：

> 让模型知道刚才聊了什么。

所以模型历史应该保存：

- 用户真实消息。
- bot 实际成功送达的消息。
- 主动消息实际成功送达的消息，并标注 `assistant:proactive`（助手主动消息）。
- 部分发送成功时，只保存成功送达部分。

不应该保存：

- 未送达消息。
- 发送失败的消息。
- 工具报错细节。
- 协议重试提示。
- guard 拦截原因。
- 内部状态机字段。
- 旧 JSON actions。
- 未经确认的长期记忆。
- 硬兜底消息，除非单独标记为系统事件，不进入普通对话历史。

---

### 5.3 记忆系统边界

记忆系统一定会加入，但第 0 层只规定边界，不规定具体算法。

记忆读取位置：

```text
BUILD_CONTEXT
→ LOAD_MEMORY_CONTEXT
```

记忆更新位置：

```text
POST_TURN_HOOKS
→ UPDATE_MEMORY
```

记忆系统允许：

- 根据当前用户、当前消息、最近历史检索相关记忆。
- 在回合结束后，从真实发生的对话中提取记忆候选。
- 写入经过过滤和确认的长期信息。

记忆系统禁止：

- 直接生成微信回复。
- 直接调用微信发送。
- 把未送达消息写入记忆。
- 把工具报错写入用户记忆。
- 把模型误解、临时猜测、玩笑直接固化为长期事实。
- 在发送前擅自改变终态。

推荐第一版记忆写入流程：

```text
回合结束
→ 提取记忆候选
→ 记忆过滤 / 去重 / 安全检查
→ 写入长期记忆
```

不建议第一版开放：

```text
write_memory
```

给模型自由调用。

可以后续开放：

```text
propose_memory_update
```

让模型只提出建议，系统审核后写入。

## 6. 输出保护规则

所有可见输出必须经过 `GUARD_OUTPUT`（输出保护）。

### 6.1 主发送路径必须 guard

```text
send_wechat_messages
→ PARSE_VISIBLE_BATCH
→ GUARD_OUTPUT
→ EXEC_SEND_WECHAT
```

禁止：

```text
send_wechat_messages
→ 直接发微信
```

### 6.2 兜底路径也必须 guard

```text
HARD_FALLBACK
→ GUARD_OUTPUT
→ EXEC_FALLBACK_SEND
```

不要因为硬兜底文案是固定的，就绕过 guard。  
统一路径比“我觉得这句安全”更可靠。

---

### 6.3 guard 失败后的流转

| guard 结果 | 流转 |
|---|---|
| 全部通过 | 进入 `EXEC_SEND_WECHAT` |
| 可安全清洗后仍有消息 | 发送清洗后消息，并记录日志 |
| 全部被拦截 | 进入 `HARD_FALLBACK` |
| 检测到协议泄露 | 进入 `HARD_FALLBACK`，不直接发模型原文 |
| 参数结构错误 | `PROTOCOL_RETRY` 一次，仍失败则 `HARD_FALLBACK` |

协议泄露示例：

```text
call_send_wechat_messages(...)
tool_calls: ...
我将调用工具...
```

这类内容不能发给用户。

## 7. 错误分类规则

不是所有错误都应硬兜底。错误要先分类。

### 7.1 可恢复错误

例子：

- 天气预取失败。
- 记忆检索失败。
- 每日总结读取失败。
- 情绪状态读取失败。
- 某个非核心上下文组件加载失败。

处理：

```text
记录日志
→ 降级继续
→ CALL_LLM
```

原则：

> 少一点上下文，总比流程直接中断好。

---

### 7.2 致命错误

例子：

- 用户消息丢失。
- 基础 system prompt 构建失败。
- 工具注册表不可用。
- 微信发送器不可用。
- 模型 API 连续失败。
- 状态机内部异常，无法判断下一状态。

处理：

```text
CLASSIFY_ERROR
→ FATAL_ERROR
→ HARD_FALLBACK 或 END_FAILED
```

如果还能发送硬兜底，则尝试发送。  
如果连微信发送器也不可用，则直接 `END_FAILED`（失败结束），只写开发日志，不写 assistant 成功历史。

---

## 8. 中断机制

微信聊天是实时系统，必须支持回合中断。

### 8.1 中断来源

可能包括：

- 用户在模型调用期间发送了新消息。
- 主动消息准备发送前，用户突然发消息。
- 当前回合被更新的用户消息合并 / 替代。
- 主动消息触发条件失效。
- 系统收到更高优先级事件。

### 8.2 中断检查点

必须在以下位置检查当前回合是否仍有效：

1. `CALL_LLM`（调用模型）返回后。
2. `GUARD_OUTPUT`（输出保护）前。
3. `EXEC_SEND_WECHAT`（执行微信发送）前。
4. 主动消息发送前。
5. 长耗时工具返回后。

### 8.3 中断终态

被中断的回合进入：

```text
END_CANCELLED（取消结束）
```

中断回合：

- 不发送旧回复。
- 不写 assistant 历史。
- 写开发日志。
- 可以写用户消息是否已被新回合吸收的记录。

## 9. 发送结果终态

### 9.1 终态列表

| 终态 | 中文含义 | 说明 |
|---|---|---|
| `END_SENT` | 全部发送成功 | 模型回复全部成功送达 |
| `END_PARTIAL_SENT` | 部分发送成功 | 批量消息中只有部分成功送达 |
| `END_SKIPPED` | 跳过结束 | 模型明确调用 `skip_reply` |
| `END_FALLBACK_SENT` | 兜底已发送结束 | 系统硬兜底成功发送，不算正常回复成功 |
| `END_FAILED` | 失败结束 | 没有完成有效可见输出 |
| `END_CANCELLED` | 取消结束 | 当前回合被新事件中断 |

---

### 9.2 发送重试规则

微信发送失败后：

```text
只重试未送达消息
```

禁止重发已送达消息。

推荐策略：

```text
初始发送 + 最多 2 次重试
```

也就是最多 3 轮尝试。

发送结果：

| 结果 | 终态 |
|---|---|
| 全部成功 | `END_SENT` |
| 部分成功 | `END_PARTIAL_SENT` |
| 全部失败 | `END_FAILED` |
| 硬兜底成功 | `END_FALLBACK_SENT` |
| 硬兜底失败 | `END_FAILED` |

---

## 10. 历史写入规则

历史是给模型看的，不是给人看的。

### 10.1 正常用户消息

用户真实消息应写入 `RECENT_HISTORY`（最近原始聊天记录）。

---

### 10.2 正常发送成功

`END_SENT`：

- 写用户消息。
- 写全部成功送达的 assistant 消息。

---

### 10.3 部分发送成功

`END_PARTIAL_SENT`：

- 写用户消息。
- 只写成功送达的 assistant 消息。
- 不写失败消息。
- 开发日志记录失败详情。

---

### 10.4 跳过回复

`END_SKIPPED`：

- 写用户消息。
- 不写 assistant 消息。

---

### 10.5 硬兜底

`END_FALLBACK_SENT`：

- 可写用户消息。
- 不建议写普通 assistant 历史。
- 可写系统事件日志。
- 如必须写入模型上下文，应单独标记为 `assistant:fallback`，避免模型误判为正常聊天内容。

---

### 10.6 失败结束

`END_FAILED`：

- 可写用户消息。
- 不写 assistant 成功回复。
- 写开发日志。

---

### 10.7 取消结束

`END_CANCELLED`：

- 不写 assistant 历史。
- 如果用户消息已被新回合吸收，则由新回合负责写入。
- 写开发日志。

---

## 11. 扩展口契约

### 11.1 `TURN_SOURCE`（回合来源）

允许来源：

- `USER_MESSAGE`（用户消息）
- `PROACTIVE_TRIGGER`（主动消息触发）
- `SYSTEM_RESUME`（系统恢复触发，未来）
- `SCHEDULED_EVENT`（定时事件，未来）

规则：

- 不同来源可以进入同一状态机。
- 主动消息不能绕过模型、guard、发送和历史写入。
- 主动消息必须标注来源，避免后续模型误以为是用户消息。

---

### 11.2 `OPTIONAL_PREPROCESS`（可选预处理）

允许：

- 预取确定性事实，如当前时间。
- 对明显天气问题预取天气。
- 做轻量分类。
- 为模型补充上下文。

禁止：

- 直接生成微信回复。
- 直接发送微信。
- 直接写 assistant 历史。
- 改变本轮终态。
- 绕过 `CALL_LLM`。

---

### 11.3 `BUILD_CONTEXT`（构建上下文）

允许加载：

- persona（人设）
- 最近历史
- 滚动摘要
- 每日摘要
- 长期记忆
- 情绪状态
- 工具结果
- 当前 turn 元信息

禁止：

- 把开发日志塞给模型。
- 把失败工具结果当成用户事实。
- 把未送达消息写进上下文。
- 把旧 JSON actions 注入上下文。

---

### 11.4 `POST_TURN_HOOKS`（回合后钩子）

允许：

- 更新摘要。
- 更新记忆。
- 更新情绪状态。
- 写开发日志。
- 写质量指标。

禁止：

- 修改本轮终态。
- 补发微信。
- 修改已经确定的发送结果。
- 把失败内容伪装成成功历史。
- 把内部错误写入模型聊天历史。

---

### 11.5 `MEMORY_LAYER`（记忆层）

允许：

- 读取相关长期记忆用于上下文。
- 回合结束后提取记忆候选。
- 经过过滤后写入长期记忆。

禁止：

- 在发送前直接影响终态。
- 自己生成可见回复。
- 记录未确认、未送达、模型猜测的内容。
- 替代 `RECENT_HISTORY`（最近历史）和 `SUMMARY_CONTEXT`（摘要上下文）。

---

## 12. 主动消息与情绪板块的接入原则

### 12.1 主动消息

主动消息不是独立发送系统。

它只是不同的 `TURN_SOURCE`（回合来源）：

```text
PROACTIVE_TRIGGER
→ CREATE_TURN
→ BUILD_CONTEXT
→ CALL_LLM
→ send_wechat_messages / skip_reply
```

主动消息必须：

- 走同一套模型调用。
- 走同一套 guard。
- 走同一套微信发送。
- 走同一套历史写入。
- 标记为 `assistant:proactive`。

---

### 12.2 情绪板块

情绪板块不直接发消息。

它只能出现在两个位置：

1. `BUILD_CONTEXT`：作为模型参考输入。
2. `POST_TURN_HOOKS`：根据本轮真实对话更新状态。

禁止：

- 情绪模块直接生成回复。
- 情绪模块直接调用微信发送。
- 情绪模块跳过主状态机。

---

## 13. 新架构必须删除或隔离的旧逻辑

以下旧逻辑不能进入新状态机：

1. `wechat_reply` 旧 action。
2. 旧 `skip` action。
3. `assistant.content` 直接发送微信。
4. `_send_fallback_text` 使用模型原文发送。
5. 旧 JSON actions 解包逻辑。
6. `already_sent` 作为核心判断字段。
7. `send_wechat_messages` tool result 回灌模型。
8. 多处不统一 fallback 文案。
9. 硬兜底绕过 guard。
10. 历史里保存旧 JSON actions。

可以保留为迁移期诊断代码，但不能作为合法主流程。

---

## 14. 第 0 层状态机必须保证的事情

第 0 层状态机不负责具体算法，但必须保证：

1. 每轮都有明确来源。
2. 每轮都有明确终态。
3. 模型必须通过原生工具调用完成动作。
4. 普通文本不能直接发微信。
5. 事实工具结果可以回灌模型。
6. 终态工具结果不能回灌模型。
7. 状态工具执行后必须回到模型或失败，不能悬空。
8. 所有可见输出必须 guard。
9. 发送失败只重试未送达消息。
10. 部分成功必须单独记录。
11. 历史只保存模型需要知道的真实聊天内容。
12. 记忆系统不能污染本轮上下文。
13. 主动消息、情绪、记忆、新工具都不能绕过主链路。
14. 错误必须分类：可恢复则降级继续，致命则兜底或失败。
15. 发生中断时，旧回合不能继续发送。

---

## 15. 一句话总则

> 不管是用户消息、主动消息、记忆系统、情绪系统，还是未来新增工具，所有微信可见输出都必须经过同一条确定主链路：模型终态工具 → 输出保护 → 微信发送 → 发送结果终态 → 历史 / 记忆 / 日志后处理。
