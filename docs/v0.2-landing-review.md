# v0.2 架构落地审查报告

审查日期: 2026-05-29 | 审查对象: `11/v0.2/` (设计总则 + 第 0 层状态机图)
对比基线: 当前 `v3` 分支代码

---

## 结论：可以落地

v0.2 的两份文档形成了一套完整、自洽的第 0 层架构。当前代码库已具备关键基础设施（`LLMGateway`、`ToolRegistry`、`output_guard`、`wechat_sender`），不需要重写整个项目。核心改造集中在一个文件（`chat_agent.py` 从过程式循环改为显式状态机）和若干配套修改。

## 一、需要新增的模块

### 1.1 `agent/state_machine.py` — 状态机引擎（核心新模块）

**职责：**

- 定义 `TurnState` 枚举（所有主状态 + 终态）
- 实现状态机主循环：`while state not in TERMINAL_STATES: dispatch(state)`
- 持有 `TurnScratchpad`（本轮临时数据，不持久化）
- 提供 `classify_tool_calls()` — 将模型 tool_calls 分为 `FACT_TOOL | TERMINAL_TOOL | STATE_TOOL | INVALID_TOOL`，并检查并行组合合法性
- 提供 `classify_error()` — 区分可恢复错误和致命错误

**关键数据结构：**

```python
class TurnState(enum.StrEnum):
    # 主状态
    RECEIVE_EVENT = "receive_event"
    CREATE_TURN = "create_turn"
    INTERRUPT_CHECK = "interrupt_check"
    BUILD_CONTEXT = "build_context"
    OPTIONAL_PREPROCESS = "optional_preprocess"
    CALL_LLM = "call_llm"
    HANDLE_MODEL_OUTPUT = "handle_model_output"
    CLASSIFY_TOOL_CALLS = "classify_tool_calls"
    EXEC_FACT_TOOLS = "exec_fact_tools"
    EXEC_STATE_TOOLS = "exec_state_tools"
    PROTOCOL_RETRY = "protocol_retry"
    TERMINAL_ACTION_BRANCH = "terminal_action_branch"
    PARSE_VISIBLE_BATCH = "parse_visible_batch"
    GUARD_OUTPUT = "guard_output"
    EXEC_SEND_WECHAT = "exec_send_wechat"
    SEND_RETRY_UNDELIVERED_ONLY = "send_retry_undelivered_only"
    DECIDE_SEND_TERMINAL = "decide_send_terminal"
    HARD_FALLBACK = "hard_fallback"
    WRITE_MODEL_HISTORY = "write_model_history"
    POST_TURN_HOOKS = "post_turn_hooks"

    # 终态
    END_SENT = "end_sent"
    END_PARTIAL_SENT = "end_partial_sent"
    END_SKIPPED = "end_skipped"
    END_FALLBACK_SENT = "end_fallback_sent"
    END_FAILED = "end_failed"
    END_CANCELLED = "end_cancelled"


class TurnScratchpad:
    """本轮临时数据。不持久化，不进入模型上下文，不进入历史。"""
    turn_id: str
    user_message: str
    trigger: str          # user / proactive / admin
    messages: list[dict]  # LLM 消息数组（仅本轮使用）
    visible_batch: list[str]        # PARSE_VISIBLE_BATCH 解析出的消息文本
    guarded_batch: list[str]        # GUARD_OUTPUT 清洗后的消息文本
    sent_results: list[dict]        # EXEC_SEND_WECHAT 每条消息的发送结果
    retry_count: int                # PROTOCOL_RETRY 已重试次数
    send_attempt: int               # SEND_RETRY 已重试次数
    fallback_events: list[dict]     # 诊断事件
    token_usage: dict               # token 统计
    error_info: dict | None         # 错误信息
```

    async def build(self, turn: TurnScratchpad, history: list[dict]) -> list[dict]:

### 1.4 `agent/send_manager.py` — 发送管理器

**职责：**

- `PARSE_VISIBLE_BATCH`：从 `send_wechat_messages` 的 tool args 中提取消息文本列表
- `GUARD_OUTPUT`：调用 `output_guard.guard_send_message_batch()`，根据结果决定流转（通过 / 清洗 / 全部拦截 / 协议泄露）
- `EXEC_SEND_WECHAT`：调用 `wechat_sender` 回调，记录每条消息的发送结果
- `SEND_RETRY_UNDELIVERED_ONLY`：筛选未送达消息，重试（当前最多 2 次重试）
- `DECIDE_SEND_TERMINAL`：根据发送结果返回 `END_SENT | END_PARTIAL_SENT | END_FAILED`

**为什么从 `chat_agent.py` 拆出：**

当前 `_handle_send_wechat_messages()` 已经 ~90 行。加上 SEND_RETRY 和终态判断后会更复杂。独立模块让 `chat_agent.py` 只做状态调度。

## 二、需要修改的模块

### 2.1 `agent/chat_agent.py` — **完全重写**（最大改动）

**当前状态：** ~560 行过程式 for 循环 + if/elif/else，混入了 tool retry、fallback、guard、发送、历史等所有逻辑。

**目标状态：** ~150 行状态机驱动入口：

```python
class ChatAgent:
    async def chat(self, ...) -> TurnResult:
        turn = TurnScratchpad(...)
        state = TurnState.CREATE_TURN

        while state not in TERMINAL_STATES:
            state = await self._dispatch(state, turn, ...)

        # POST_TURN_HOOKS 由 main.py 在拿到 TurnResult 后调用
        return TurnResult(
            terminal_state=state,
            visible_messages=turn.guarded_batch,
            sent_results=turn.sent_results,
            fallback_events=turn.fallback_events,
            token_usage=turn.token_usage,
            turn_id=turn.turn_id,
            ...
        )

    async def _dispatch(self, state, turn, ...) -> TurnState:
        """每个状态一个处理方法，返回下一个状态"""
        ...
```

**ChatAgent 不再负责：**
- 直接拼 `all_messages`（由 `turn_context.py` 的 `ContextBuilder` 负责）
- 解析 send_wechat_messages 参数（由 `send_manager.py` 负责）
- guard 和微信发送（由 `send_manager.py` 负责）
- 写历史（由 `main.py` 根据终态写）
- hard fallback 的具体文案和发送（由 `send_manager.py` 负责）

## 四、推荐的分阶段落地顺序

### Phase 1：状态机核心 + 工具分类（预计改动最大，风险最高）

**目标：** 替换 `chat_agent.py` 的过程式循环为显式状态机。保证核心分支（send / skip / fact tool / protocol retry / hard fallback）全部正确。

**具体改动：**

1. 新建 `agent/state_machine.py`：`TurnState` 枚举 + `TurnScratchpad` 数据类 + 状态机 dispatcher
2. 新建 `agent/tool_classifier.py`：`ToolCategory` 枚举 + `classify_tool_calls()` + 并行工具合法性检查
3. 修改 `agent/tool_registry.py`：
   - `ToolDef` 增加 `tool_category` 字段
   - 注册 `skip_reply` 为 `TERMINAL_TOOL` + `native_tool_call_eligible=True`
   - 删除 `wechat_reply` / `skip` action
   - 删除 `search_memory` / `send_email` / `read_persona_file` / `propose_persona_change`
4. **重写 `agent/chat_agent.py`**：`chat()` 改为状态机驱动
5. 修改 `config.yaml`：`allowed_tools` 增加 `skip_reply`
6. 修改 `prompts/base_protocol.md` + `tool_policy.md`：添加 `skip_reply` 说明

**验收标准：**

- [ ] 模型调用 `send_wechat_messages` → 消息正确发送到微信 → `END_SENT`
- [ ] 模型调用 `skip_reply` → 不发微信 → `END_SKIPPED`
- [ ] 模型调用 `get_time` / `get_weather` → 结果回灌模型 → 模型继续推理 → 最终必须调终态工具
- [ ] 模型只输出 `assistant.content`（无 tool_calls）→ `PROTOCOL_RETRY` → 注入系统提醒 → 回到 `CALL_LLM`
- [ ] `PROTOCOL_RETRY` 超限 → `HARD_FALLBACK` → 系统固定文案 → `END_FALLBACK_SENT`
- [ ] `send_wechat_messages` 成功后 **不** 把 "已发送 N/M 条" 注入 messages
- [ ] `assistant.content` **绝对不** 直接发到微信（任何路径）
- [ ] 旧 JSON actions（`{"actions":[...]}`）不被解析为合法动作 — 视为 `assistant.content only` → `PROTOCOL_RETRY`
- [ ] LLM error → `HARD_FALLBACK` → 系统固定文案 → `END_FALLBACK_SENT` / `END_FAILED`
- [ ] 所有现有测试要么通过，要么更新为匹配新行为（不允许悄悄的回归）

---

### Phase 2：Guard 统一 + 发送重试 + 硬兜底统一

**目标：** 所有出站路径统一走 guard + wechat_sender。实现 SEND_RETRY。

**具体改动：**

1. 新建 `agent/send_manager.py`：
   - `PARSE_VISIBLE_BATCH`：从 tool args 提取消息文本
   - `GUARD_OUTPUT`：调用 `output_guard.guard_send_message_batch()`
   - `EXEC_SEND_WECHAT`：调用 `wechat_sender`
   - `SEND_RETRY_UNDELIVERED_ONLY`：筛选未送达消息，最多 2 次重试
   - `DECIDE_SEND_TERMINAL`：`all delivered → END_SENT | partial → END_PARTIAL_SENT | all failed → END_FAILED`
2. 修改 `agent/output_guard.py`：
   - 统一 `HARD_FALLBACK_TEXT`
   - 删除旧 JSON actions 解包逻辑
3. 修改 `main.py` 的 `wechat_sender`：职责缩减为纯粹发送（guard 已在上游完成）
4. 确保硬兜底也经过 `GUARD_OUTPUT` → `EXEC_FALLBACK_SEND`

**验收标准：**

- [ ] `send_wechat_messages` 的消息必须经过 `guard_send_message_batch()` 才能发微信
- [ ] 硬兜底消息也经过 `guard_single_message()` 才能发微信
- [ ] 协议泄露内容（`call_xxx`、`tool_calls` 等）被 guard 拦截，不发给用户
- [ ] 微信发送失败（网络错误等）→ 系统自动重试同一批未送达消息（不重新调模型）
- [ ] 重试 2 次后仍失败 → `END_FAILED`
- [ ] 3 条消息中 2 条送达 1 条失败 → `END_PARTIAL_SENT`
- [ ] 硬兜底文案全局统一为一种
- [ ] `HARD_FALLBACK_TEXT` 常量在 `output_guard.py` 中定义，全局引用

2. 修改 `agent/context_builder.py`：删除 legacy 函数，保留 `compact_history()` 和 `build_chat_system_prompt()`（移入 `turn_context.py`）
3. 修改 `main.py`：
   - `/chat` 端点根据 `result.terminal_state` 分发历史写入逻辑（见 2.6 的 match-case）
   - 在回合结束后调用 `POST_TURN_HOOKS`（当前为空，架构位置预留）
   - 删除 `_assistant_history_json()`
4. 清理 `main.py` 中 `persona`/`personality` 语义混乱

**验收标准：**

- [ ] `END_SENT` → 写用户消息 + 全部 assistant 消息
- [ ] `END_PARTIAL_SENT` → 写用户消息 + 仅成功送达的 assistant 消息
- [ ] `END_SKIPPED` → 写用户消息，不写 assistant 消息
- [ ] `END_FALLBACK_SENT` → 写用户消息，不写普通 assistant（或单独标记为 system:fallback）
- [ ] `END_FAILED` / `END_CANCELLED` → 可写用户消息，不写 assistant 成功回复
- [ ] 模型历史中不含：tool_call_id、协议重试提示、guard 拦截信息、未送达消息
- [ ] `ContextBuilder._memory_loader` 注入点存在（默认 `None`），可被未来记忆模块挂载
- [ ] `POST_TURN_HOOKS` 中的 `UPDATE_MEMORY` 钩子存在（默认 no-op），可被未来记忆模块挂载
- [ ] 旧 JSON actions 格式不出现在任何写入历史的路径中

### Phase 4：中断检查 + 错误分类

**目标：** 实现回合中断机制和错误分类。这一阶段可以延后——当前单用户场景下中断概率低，但架构上应先预留位置。

**具体改动：**

1. 在状态机的 `INTERRUPT_CHECK` 位置实现检查逻辑（当前可通过 per-user lock 简化：同一用户的新消息到来时，旧回合的 `INTERRUPT_CHECK` 返回 `True`）
2. 实现 `CLASSIFY_ERROR`：区分可恢复错误（降级继续）和致命错误（`HARD_FALLBACK` 或 `END_FAILED`）
3. 在 `CALL_LLM` 返回后、`GUARD_OUTPUT` 前、`EXEC_SEND_WECHAT` 前放置 `INTERRUPT_CHECK`

**验收标准：**

- [ ] 用户在模型推理期间发新消息 → 旧回合 `END_CANCELLED`，旧回复不发微信
- [ ] 记忆检索失败 → 可恢复错误，降级继续（不带记忆上下文调模型）
- [ ] 基础 prompt 构建失败 → 致命错误 → `HARD_FALLBACK`
- [ ] 微信发送器不可用 → 致命错误 → `END_FAILED`

## 五、风险点和建议

### 5.1 最大风险：模型不遵守协议

即使 prompt 明确要求调用终态工具，DeepSeek 模型仍可能输出 `assistant.content` 而不调用 tool_calls。这会导致频繁进入 `PROTOCOL_RETRY`，增加延迟和 token 消耗。

**缓解措施：**
- `base_protocol.md` 中把规则放在最前面，用强调语气
- 考虑在 `tool_choice` 参数上做实验：是否可以设为 `"required"` 强制模型必须调用工具？但这样模型在应该 skip 时也必须调 `skip_reply`，需要测试
- `PROTOCOL_RETRY` 上限设为 1 次（而非更多），减少无效重试

### 5.2 旧 JSON actions 的硬着陆

当前 prompt 已经从 JSON actions 迁移到 native tool calls。但如果模型训练数据中仍有旧格式的强关联，偶尔仍会输出旧格式。v0.2 明确不兼容旧格式，意味着这些 case 会进 `PROTOCOL_RETRY` → `HARD_FALLBACK`。

**缓解措施：**
- `PROTOCOL_RETRY` 的系统提醒中，明确说 "请使用工具调用，不要在手写 JSON"
- 监控 `fallback_events` 中 `protocol_retry` 的频率，如果超过 5% 需要调整 prompt

### 5.3 发送重试的"已送达"判定

微信 iLink 的 `send_text` 返回成功，是否一定意味着用户收到了？如果 iLink 返回成功但实际未送达（如用户已删好友），重试没有意义。

**建议：**
- `SEND_RETRY` 只针对明确的网络错误（timeout、connection error），不针对 iLink 的业务错误码
- iLink 返回业务错误（如 `contact_not_found`）时直接 `END_FAILED`，不重试

### 5.4 工具分类的边界

`STATE_TOOL` 在当前版本没有实例。但 `tool_classifier.py` 的分类逻辑和 `EXEC_STATE_TOOLS` 状态应保留。这避免了未来加记忆工具时在主流程里临时开分支。

### 5.5 `ActionRegistry` 的去留

当前 `ActionRegistry` 只有 `wechat_reply` 和 `skip`。v0.2 要求删除它们。问题是：`ActionRegistry` 这个类本身还要保留吗？

**建议：** 保留 `ActionRegistry` 类的定义（代码量很小），但清空注册项。未来如果有不需要暴露给模型但需要系统解释的内部动作（如 SYSTEM_HOOK 的某些实现），可以放回 ActionRegistry。
