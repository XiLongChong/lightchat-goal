### 7.3 `_determine_trigger_mode`（反馈一·第 1 点核心逻辑）

```python
def _determine_trigger_mode(
    self,
    settings: ProactiveSettings,
    now_ts: float,
) -> tuple[str | None, str | None]:
    """基于 last_visible_message_at + 强度档位判断 optional/required。

    Returns (trigger_mode, block_reason):
      - ("optional", None)  → 可进入 optional trigger
      - ("required", None)  → 必须进入 required trigger
      - (None, "too_early") → 未到时间，不触发

    反馈一·第 1 点: 统一基于 last_visible_message_at，不用 last_user_message_at。
    """
    last_visible = await self._store.get_last_visible_message_at(user_id, bot_id)
    if last_visible <= 0:
        return (None, "no_visible_message_yet")

    elapsed = now_ts - last_visible
    profile = get_intensity_profile(settings.autonomous.intensity)

    if elapsed >= profile["required_after_minutes"] * 60:
        return ("required", None)
    elif elapsed >= profile["optional_after_minutes"] * 60:
        return ("optional", None)
    else:
        return (None, "too_early")
```

### 7.4 `last_visible_message_at` 读取

scheduler 直接从 `dialogue_state.last_visible_message_at` 读取。**不再**计算 `max(last_user, last_assistant)`。

更新规则（反馈一·第 5 点）：

| 触发事件 | 是否更新 `last_visible_message_at` |
|---|---|
| 用户消息写入 `conversation_history` | **是** |
| assistant 消息 `SENT_CONFIRMED` | **是** |
| dry-run | **否** |
| 发送失败 | **否** |
| guard blocked | **否** |
| `UNKNOWN_AFTER_ATTEMPT` | **否** |

### 7.5 数据库迁移回填（反馈一·第 5 点）

`last_visible_message_at` **不能默认为 0 直接参与判断**。迁移逻辑（在 `_migrate()` 中）：

```
1. ALTER TABLE dialogue_state ADD COLUMN last_visible_message_at
2. 回填：
   a. 从 conversation_history 取最后一条可见消息时间:
        - 最后一条 role=user 的消息 ts
        - 最后一条 role=assistant 且 source 不是 "assistant:fallback" 的消息 ts
        - 取 max
   b. 如果无法回填（DB 为空），初始化为当前时间 time.time()
      （避免升级后立刻进入 required trigger）
```

### 7.6 `run_heartbeat` 改动

```
heartbeat tick
→ _check_eligibility:  (反馈一·第 1 点: 不检查 user message quiet window)
    → settings.enabled == false? → skip
    → settings.autonomous.enabled == false? → skip
    → daily_active_message_cap reached? → skip
    → daily_autonomous_trigger_cap reached? → skip
    → bridge / quiet_hours / user_opt_out / scheduler_busy
→ _determine_trigger_mode:
    → last_visible_message_at <= 0? → skip (no_visible_message_yet)
    → elapsed < optional_after? → skip (too_early)
    → optional_after <= elapsed < required_after → "optional"
    → elapsed >= required_after → "required"
→ scheduler 构建 impulse_meta:
    → optional: trigger_mode="optional", trigger_kind="autonomous",
      trigger_source 来自 impulse pipeline 选择 (PRESENCE/ECHO/TOPIC_CONTINUE)
    → required: trigger_mode="required", trigger_kind="autonomous",
      trigger_source="REQUIRED_PRESENCE"
→ _execute_proactive_turn(impulse_meta)
```

## 8. `agent/chat_agent.py` 改动 — 主动回合工具约束（反馈一·第 2 点）

### 8.1 约束矩阵

当 `source=SOURCE_PROACTIVE_IMPULSE` 时，按以下规则限制工具：

**`proactive_delivered_count == 0`（尚未发出任何用户可见消息）：**

| trigger_mode | wechat_reply | skip_proactive | done | fact tools |
|---|---|---|---|---|
| optional | 允许 | 允许 | **禁止** | 允许 |
| required | 允许 | **禁止** | **禁止** | 允许 |

**`proactive_delivered_count > 0`（已至少发出一条用户可见消息）：**

| trigger_mode | wechat_reply | skip_proactive | done | fact tools |
|---|---|---|---|---|
| optional | 允许 | **禁止** | 允许 | 允许 |
| required | 允许 | **禁止** | 允许 | 允许 |

核心规则：

- delivered_count == 0 时：**任何 trigger_mode 下 done 都禁止**。optional 用 `skip_proactive` 退出，required 必须先调 `wechat_reply`。
- delivered_count > 0 时：done 恢复可用。skip_proactive 全程禁止（已发过消息不能用 skip 退出）。
- done 是统一终态工具，**不新增 done_proactive**。

**约束 #1：required trigger + delivered_count==0 时 fact tools 最多 1 次**：

| 限制项 | 值 |
|---|---|
| 最多连续 fact tool 调用次数 | 1 次 |
| fact tool 回灌后下一步必须调用 | `wechat_reply` |
| 如果继续调用 fact tool、done 或 skip_proactive | 视为协议错误 → `PROTOCOL_RETRY` |
| 计数方式 | `scratchpad` 新增 `_proactive_fact_tool_count_since_last_reply` 字段 |

可选 trigger 不受此限制（模型可以在发消息前多次调用 fact tools）。

**约束 #2：`assistant_messages_after_last_user` 只能来自 `conversation_history` 中已写入的可见历史**。
不得包含 dry-run / send failed / guard blocked / attempts / debug_runs 内容。这些内容不应出现在 `conversation_history` 中，但如果存在也必须被过滤。

### 8.2 约束执行位置

**双层保护**：

1. **allowed_tools 裁剪**（prompt 层）：`build_chat_system_prompt` 根据 `proactive_meta` 和当前 `proactive_delivered_count` 动态生成可用工具列表，不把禁止的工具暴露给模型。

2. **tool_classifier 硬拦截**（执行层）：即使模型绕过 prompt 调用了被禁工具，`CLASSIFY_ONE_TOOL_CALL` 阶段做硬校验：

```python
def _validate_proactive_tool_constraints(
    tool_name: str, tool_args: dict, scratchpad: TurnScratchpad,
) -> str | None:
    """反馈一·第 2 点: 后端硬校验，不只依赖 allowed_tools。

    Returns None if valid, or error message string.
    """
    if scratchpad.source != SOURCE_PROACTIVE_IMPULSE:
        return None  # 非主动回合不检查

    delivered = scratchpad.proactive_delivered_count
    trigger_mode = scratchpad.proactive_meta.get("trigger_mode", "") if scratchpad.proactive_meta else ""

    # done: delivered_count==0 时一律禁止
    if tool_name == "done" and delivered == 0:
        return f"done is not allowed before first delivery (delivered_count=0, trigger_mode={trigger_mode})"

    # skip_proactive: delivered_count>0 后一律禁止
    if tool_name == "skip_proactive" and delivered > 0:
        return "skip_proactive is not allowed after first delivery"

    # skip_proactive: required trigger 全程禁止
    if tool_name == "skip_proactive" and trigger_mode == "required":
        return "skip_proactive is not allowed in required trigger mode"

    # 约束 #1: required + delivered_count==0 → fact tools max 1
    if tool_name in FACT_TOOL_NAMES and trigger_mode == "required" and delivered == 0:
        if scratchpad._proactive_fact_tool_count_since_last_reply >= 1:
            return "only 1 fact tool call allowed before first wechat_reply in required trigger mode"

    return None
```

fact tool 计数在 `EXEC_FACT_TOOLS` 成功后递增。`wechat_reply` 成功交付后归零。

违规 → `PROTOCOL_RETRY`。

### 8.3 Required trigger 失败处理（反馈一·第 3 点）

| 失败类型 | 处理 |
|---|---|
| guard 拦截 | 允许模型重试 1 次（复用现有 protocol retry 机制），仍失败 → `END_PROACTIVE_GUARD_BLOCKED` |
| LLM API 错误 | 记录 `required_trigger_failed_model`，`END_FAILED_NO_FALLBACK` |
| 协议违规（PROTOCOL_RETRY 耗尽） | `END_PROTOCOL_ERROR` |
| 模型调了 skip_proactive 或 done（被硬拦截） | `PROTOCOL_RETRY`；重试仍违规 → `END_PROTOCOL_ERROR` |

**不使用固定兜底文案。** 失败不写可见历史。

**改动清单**：
- `agent/chat_agent.py`：~80 行（动态 allowed_tools、CLASSIFY_ONE_TOOL_CALL 硬校验、required trigger 错误路径）
- `agent/tool_classifier.py`：~25 行（`_validate_proactive_tool_constraints`）

### 9.2 `last_visible_message_at` 更新方法（反馈一·第 5 点）

```python
async def update_last_visible_message_at(
    self, user_id: str, bot_id: str, ts: float,
    source: str,  # "user_message" | "assistant_sent_confirmed"
) -> bool:
    """反馈一·第 5 点: 仅接受两个合法来源。"""
    if source not in ("user_message", "assistant_sent_confirmed"):
        raise ValueError(
            f"last_visible_message_at only accepts "
            f"user_message or assistant_sent_confirmed, got {source}"

    # upsert to dialogue_state
```

| 位置 | source |
|---|---|
| `main.py: _record_user_message_arrival` | `"user_message"` |
| `chat_agent.py: EXEC_SEND_ONE` → post_turn_hook | `"assistant_sent_confirmed"` |

### 9.3 `daily_autonomous_trigger_count` 更新语义（反馈一·第 4 点）

**只计数成功完成的 Bot 自主主动触发**。在 POST_TURN_HOOKS 中有一个 dedicated hook：

```python
async def _hook_bump_autonomous_trigger_count(
    turn: TurnScratchpad, terminal_state: TurnState,
) -> None:
    """反馈一·第 4 点: 只在成功完成时 +1。"""
    meta = turn.proactive_meta or {}
    if turn.source != SOURCE_PROACTIVE_IMPULSE:
        return
    if meta.get("trigger_kind") != "autonomous":
        return
    if terminal_state != TurnState.END_REPLIED:
        return
    if turn.proactive_delivered_count == 0:
        return
    # 全部条件满足 → 计数 +1
    await store.bump_autonomous_trigger_count(user_id, bot_id)
```

**不计入**：too_early、eligibility failed、no impulse selected、skip_proactive、guard blocked、send failed、protocol error、LLM error、dry-run。

可另记 `autonomous_attempt_count` 用于诊断，但不参与频率上限。

### 9.4 迁移回填逻辑（反馈一·第 5 点）

在 `_migrate()` 中，新增列后的回填步骤：

```python
# 1. 新增列

# 2. 回填已有数据
rows = await db.execute_fetchall(
    "SELECT user_id, bot_id FROM dialogue_state"
)
for row in rows:
    uid, bid = row["user_id"], row["bot_id"]
    # 从 conversation_history 查找最后一条可见消息
    cur = await db.execute_fetchall(
        """SELECT MAX(ts) as last_ts FROM conversation_history
           WHERE user_id = ? AND bot_id = ?
             AND (role = 'user'
                  OR (role = 'assistant' AND source != 'assistant:fallback'))""",
        (uid, bid),
    )
    backfill_ts = cur[0]["last_ts"] if cur and cur[0]["last_ts"] else time.time()
    await db.execute(
        "UPDATE dialogue_state SET last_visible_message_at = ? WHERE user_id = ? AND bot_id = ?",
        (backfill_ts, uid, bid),
    )
```

## 18. 关键决策记录

1. **默认值继承**：`load_proactive_settings` 首次从 `config.features.proactive` 取值，保存后 `runtime_settings.json` 为权威来源。

2. **统一基于 last_visible_message_at 的频率判断**：不使用 `last_user_message_at` 或 user message quiet window。用户视角不区分上一条是用户消息/bot 回复/bot 主动消息，只要是可见的最后一条就作为计时起点。elapsed 基于 `now - last_visible_message_at` 计算，对照强度档位的 `optional_after` / `required_after` 决定 trigger_mode。

3. **首条前工具约束**：`proactive_delivered_count == 0` 时 done 一律禁止（无论 optional/required）。optional 用 `skip_proactive` 退出，required 必须先调 `wechat_reply`。双层保护：allowed_tools 裁剪 + tool_classifier 硬拦截。不新增 done_proactive。

4. **Required trigger 不是兜底发文**：required 的含义是 "到了最迟触发时间必须认真进入主动生成流程，模型必须至少尝试 wechat_reply"。guard 拦截可重试，API 失败记录后终止。不使用固定兜底文案，失败不写可见历史。

5. **daily_autonomous_trigger_count 只计成功完成**：source=PROACTIVE_IMPULSE + trigger_kind=autonomous + terminal_state=END_REPLIED + delivered_count>0 全部满足才 +1。不计入 skip/guard_block/send_failed/protocol_error/LLM_error/dry-run。

6. **last_visible_message_at 更新规则**：仅用户消息写入 history + assistant SENT_CONFIRMED 更新。迁移回填优先从 conversation_history 取，空 DB 初始化为当前时间避免升级后立刻 required。

7. **双上限**：`daily_autonomous_trigger_cap` 来自强度档位（统计成功完成次数），`daily_active_message_cap` 默认 50（统计主动类真实送达消息条数）。required trigger 受两者约束。

8. **V1.6-A 隐藏未生效设置**：用户定时消息、08:00/23:00、自定义任务在前端不展示。

9. **Settings 校验**：intensity 枚举、daily cap 1-200、quiet hours HH:mm、bool 开关。config.yaml 仅首次默认值。

10. **拆分实施**：V1.6-A → V1.6-B → V1.6-C 顺序交付。

11. **独立 router**：设置接口放 `admin_proactive_settings_routes.py`，DI 注入。

12. **上下文字段截断**：`last_user_message` ≤ 500 字，`assistant_messages_after_last_user` ≤ 6 条 × 300 字。

13. **强度不影响人格**：intensity 只传入 scheduler，不传入 prompt。模型只能看到 `trigger_mode: optional/required`。

14. **定时任务进入同一回路**：所有定时消息走 `ProactiveScheduler → ChatAgent → guard → send`。

15. **共用 proactive lock**：所有 proactive 入口通过同一 `_lock` 互斥。
