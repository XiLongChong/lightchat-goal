## 四、旧 JSON actions 在新架构下的最终行为

### 核心原则

v0.2 **不兼容旧 JSON actions**。`assistant.content` 里的 `{"actions": [...]}` 被视为普通文本，不作为合法动作解析。

### 三条路径的行为

**路径 A：模型在 assistant.content 中输出旧 JSON actions（无 tool_calls）**

```
HANDLE_MODEL_OUTPUT 检测到 assistant.content 无 tool_calls
→ 如果内容包含 "actions" → 标记 "old_json_actions_detected"
→ PROTOCOL_RETRY (最多 1 次，不注入 assistant.content)
→ 超限后 HARD_FALLBACK → 系统固定文案 "我刚刚卡了一下 重新说"
→ END_FALLBACK_SENT 或 END_FAILED
```

**路径 B：旧 JSON actions 作为 send_wechat_messages 的参数内容**

```
PARSE_VISIBLE_BATCH 提取 messages 数组
→ GUARD_OUTPUT 调用 guard_send_message_batch
→ _has_protocol_leak 调用 _looks_like_protocol_json 检测
→ 检测到 "actions" + "wechat_reply" → 硬阻断
→ 返回 HARD_FALLBACK_TEXT，不发送模型原文
```

**路径 C：旧 JSON actions 出现在历史记录中**

```
_format_history_entry 不做 JSON 解包
→ _extract_visible_text 只剥离 call_xxx 污染
→ 旧 JSON 作为纯文本保留（历史中），但模型上下文中的旧格式
  会被 HANDLE_MODEL_OUTPUT 检测到 → PROTOCOL_RETRY
```

### 已删除的旧逻辑

| 旧逻辑 | 状态 |
|--------|------|
| `_unwrap_nested_protocol()` | ✅ 已从 `output_guard.py` 删除 |
| `_extract_nested_protocol_reply` 别名 | ✅ 已删除 |
| `_sanitize_outbound_text` 别名 | ✅ 已删除 |
| `guard_single_message` 中的 JSON unwrap 步骤 | ✅ Phase 2 已替换为 `_has_protocol_leak` 硬阻断 |
| `_extract_visible_text` 中的 JSON actions 解析 | ✅ Phase 1 已删除 |
| `_assistant_history_json()` | ✅ Phase 1 已删除 |

### 保留的检测逻辑

`_looks_like_protocol_json()` **保留**，仅用于 `_has_protocol_leak`（`guard_send_message_batch` 的协议泄露检测），触发硬阻断，**不 unwrap 成可发送文本**。

## 九、未完成的 gap（按事实描述）

### Gap #1: `OPTIONAL_PREPROCESS` 未实现

- **设计要求**: 状态机图在 `BUILD_CONTEXT` 和 `CALL_LLM` 之间有 `OPTIONAL_PREPROCESS` 用于预取事实
- **当前状态**: `TurnState` 枚举中有 `OPTIONAL_PREPROCESS` 成员，但 `_dispatch` 未处理该状态。无 handler 实现。
- **影响**: 天气查询等场景需要模型先调 `get_weather` 再调 `send_wechat_messages`，多一轮 LLM 调用。非阻断。

### Gap #2: `INTERRUPT_CHECK` 未在 main.py 接线

- **设计要求**: 状态机在 main.py 中注入 `InterruptChecker` 回调，检测用户新消息并取消旧回合
- **当前状态**: `ChatAgent.set_interrupt_checker()` 存在，3 个检查点存在。但 main.py **未调用** `set_interrupt_checker()`。per-user `asyncio.Lock` 保证串行处理。
- **影响**: 当前单用户场景无影响。**主动消息接入时必须接线**。

### Gap #3: `INTERRUPT_CHECK` 未覆盖 `CREATE_TURN` 后和长耗时工具后

- **设计要求**: 状态机图在 `CREATE_TURN` 之后和"长耗时工具返回后"有中断检查点
- **当前状态**: 仅 3 个检查点（`HANDLE_MODEL_OUTPUT`、`GUARD_OUTPUT`、`EXEC_SEND_WECHAT`）。`CREATE_TURN` 后的检查未实现（当前无实际中断源）。无长耗时工具故该检查点不需要。
- **影响**: 低。与 Gap #2 同源。

### Gap #4: 死 prompt 文件

以下文件不再被 `build_chat_system_prompt` 加载，但仍存在：

| 文件 | 原因 |
|------|------|
| `prompts/bot_identity_default.md` | 多 bot 已关闭 |
| `prompts/relationship_context.md` | 关系追踪已关闭 |
| `prompts/memory_policy.md` | 引用已删除的 `search_memory` 工具 |
| `prompts/trigger_context.md` | 未被加载（当前只加载 base_protocol + tool_policy） |

`memory_policy.md` 含对 `search_memory` 的引用——该工具已从注册表中删除。此文件不参与任何运行时路径。

## 十一、总结

v0.2 第 0 层架构已完整落地。核心总则全部满足：

> 所有微信可见输出都必须经过同一条确定主链路：
> **模型终态工具 → 输出保护 → 微信发送 → 发送结果终态 → 历史/记忆/日志后处理**

剩余 4 个 gap 均为架构预留或简化的非核心项。主动消息接入时需要处理 Gap #2（中断检查接线）。
