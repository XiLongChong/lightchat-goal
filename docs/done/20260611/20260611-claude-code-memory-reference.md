# Claude Code 记忆方案分析参考（2026-06-11）

> 适用场景：24 小时在线、单用户、长期运行的私人陪伴 Agent
> 参考：Claude Code 记忆系统源码逆向分析，按需裁剪
>
> 归档说明：本文是设计过程中的分析参考稿，包含若干未采用或后来调整的方案。
> 最终产品决策和已实现行为以同目录的
> `20260611-memory-system.md` 为准，不应直接按本文继续实施。

---

## 0. 设计前提与约束

| 约束 | 影响 |
|------|------|
| 24 小时在线，不频繁重启 | 记忆不需要"跨会话恢复"，而需要"跨压缩恢复" |
| 单用户私人陪伴 | 去掉团队记忆、项目隔离、scope 路由 |
| 固定每日压缩 | 压缩窗口是记忆提取的最佳时机 |
| 压缩产物存数据库 | 会话记忆走 DB，长期记忆走 .md 文件 |
| 无项目上下文 | 去掉 project 类型，记忆类型面向"人"而非"代码" |
| 偶尔做定时任务 | 记忆系统需要支持"待办/提醒"类信息 |

**核心命题**：对于 24/7 陪伴 Agent，"遗忘"只发生在压缩时刻。记忆系统的首要任务是——**压缩后，Agent 仍然知道自己是谁、用户是谁、关系到了哪一步。**

## 1. 记忆分层架构

```
┌─────────────────────────────────────────────────────┐
│                   实时对话上下文                       │
│              （context window，会被压缩）               │
├─────────────────────────────────────────────────────┤
│                   会话记忆 Session Memory              │
│     压缩产物，存 DB，结构化 Markdown，压缩后加载        │
├─────────────────────────────────────────────────────┤
│                   长期记忆 Long-term Memory            │
│     .md 文件 + MEMORY.md 索引，压缩后加载，跨天持久     │
├─────────────────────────────────────────────────────┤
│                   每日日志 Daily Log                   │
│     .md 文件，append-only，供整合阶段回溯               │
└─────────────────────────────────────────────────────┘
```

各层职责：

| 层 | 何时写入 | 何时读取 | 生命周期 |
|----|---------|---------|---------|
| 会话记忆 | 每日压缩时 | 压缩后立即加载到上下文 | 到下一次压缩时被覆盖 |
| 长期记忆 | 压缩时提取 + 用户主动要求 | 压缩后加载 MEMORY.md；对话中按需检索 | 永久（直到被整合删除） |
| 每日日志 | 对话中实时追加 | 整合阶段回溯 | 整合后可归档/删除 |

## 2. 长期记忆：类型分类体系

Claude Code 的四种类型（user/feedback/project/reference）是面向代码项目的。陪伴 Agent 需要面向"人与关系"重新设计。

### 四种记忆类型

#### type: `user`（用户画像）

> **存什么**：用户是谁——身份、性格、处境、人生阶段
> **何时存**：了解到用户的任何身份信息、性格特征、生活状况时
> **怎么用**：决定沟通风格、共情方向、话题选择

示例：
```markdown
---
name: user-profile
description: 用户是一名互联网产品经理，30岁，独居，性格内向但有幽默感
type: user
---

## 基本信息
- 职业：互联网产品经理，在一家中型公司
- 年龄：30岁
- 居住：独居，养了一只橘猫叫"饺子"
- 性格：内向但有冷幽默，不喜欢过度热情的回应
- 生活节奏：夜猫子，通常凌晨1-2点睡

**Why:** 沟通风格应偏温和克制，避免热情过度；晚间对话可以更随意
**How to apply:** 主动寒暄时用轻松而非热烈的方式；晚上11点后可以聊更轻松的话题
```

#### type: `preference`（偏好与边界）

> **存什么**：用户希望你怎么做——纠正和确认都记
> **何时存**：用户纠正你的行为，或确认你的做法"就是这样"时
> **怎么用**：维持行为一致性，不让用户反复教同一件事

示例：
```markdown
---
name: preference-communication-style
description: 用户偏好简洁回应，不喜欢总结式结尾，讨厌被说教
type: preference
---

## 规则
回应要简洁自然，像朋友聊天不像客服。不要在每段话结尾总结刚才说了什么。

**Why:** 用户明确说"你能不能别每次都总结，我又不是没看懂"（2025-06-08）
**How to apply:** 回复完就停，不追加"所以总的来说..."；如果用户没问建议，别主动给建议
```

#### type: `event`（生活事件）

> **存什么**：用户生活中发生的重要事件——里程碑、变故、计划、待办
> **何时存**：用户提到生活中发生了什么事，尤其是有情绪分量的事
> **怎么用**：跟进事件进展、在适当时机关心、维护待办提醒

示例：
```markdown
---
name: event-job-interview
description: 用户2025-06-15有一场重要面试，是跳槽的关键机会
type: event
---

## 事件
- 日期：2025-06-15
- 事件：某大厂终面
- 背景：用户在现公司待了3年想跳槽，这是最看重的一个机会
- 情绪：紧张但也很期待

**Why:** 这是用户近期最重要的事，需要在面试前给予鼓励，面试后主动关心结果
**How to apply:** 6月14日晚可以主动聊面试准备缓解紧张；6月15日当天少打扰；6月16日跟进结果
```

#### type: `knowledge`（用户知识）

> **存什么**：用户希望你记住的零散事实——人名、习惯、喜好、梗
> **何时存**：用户说"记住这个"或提到某个反复出现的主题
> **怎么用**：在相关话题出现时引用，让用户感到被理解

示例：
```markdown
---
name: knowledge-cat-dumpling
description: 用户的橘猫叫饺子，是2023年领养的，有分离焦虑
type: knowledge
---

## 关于饺子
- 名字：饺子（因为胖且白）
- 品种：橘猫
- 领养时间：2023年
- 特点：有分离焦虑，用户出门会叫很久
- 用户很爱它，经常发它的照片

**Why:** 饺子是用户生活中重要的陪伴，提到饺子时用户会开心
**How to apply:** 用户说"饺子又在叫"时要共情而非敷衍；可以偶尔主动问饺子近况
```

### 什么不要存

```
## 不要存入长期记忆
- 临时情绪和心情 → 这些属于会话记忆，会在压缩时处理
- 对话中的闲聊内容 → 日志里记录即可，不值得提升为长期记忆
- 可以从其他记忆推导的信息 → 比如已知用户是产品经理，不需要再存"用户懂PRD"
- 任何用户说"忘了这个"的内容 → 立即删除对应记忆
- 过于具体的对话细节 → 存结论不存过程
```

## 3. 长期记忆：存储格式

### 3.1 记忆文件格式

每条记忆 = 一个 `.md` 文件，固定 frontmatter：

```markdown
---
name: <kebab-case 短名称>
description: <一句话描述，用于检索时匹配，越具体越好>
type: <user | preference | event | knowledge>
created: <ISO 日期，首次创建时间>
updated: <ISO 日期，最后更新时间>
---

{{正文内容}}

{{如果是 preference/event 类型，追加：}}
**Why:** <为什么这条记忆重要——用户的原话或背景>
**How to apply:** <什么场景下该想起这条记忆>
```

**与 Claude Code 的差异**：
- 新增 `created` / `updated` 时间戳（Claude Code 依赖文件 mtime，但我们用显式字段更可靠）
- 去掉 `scope` 字段（不需要团队/私有区分）
- `type` 值不同：`user/preference/event/knowledge` 替代 `user/feedback/project/reference`

### 3.2 文件命名规范

```
<type>-<name>.md
```

示例：
```
user-profile.md
preference-communication-style.md
event-job-interview.md
knowledge-cat-dumpling.md
```

### 3.3 目录结构

```
memory/
├── MEMORY.md                        # 索引文件
├── user-profile.md                  # 用户画像
├── preference-communication-style.md # 沟通偏好
├── event-job-interview.md           # 重要事件
├── knowledge-cat-dumpling.md        # 用户知识
├── ...                              # 更多记忆文件
└── logs/                            # 每日日志
    └── 2025/
        └── 06/
            ├── 2025-06-10.md
            └── 2025-06-11.md
```

**与 Claude Code 的差异**：
- 不按 type 分子目录——记忆量小（预计 <50 条），扁平结构更简单
- 日志子目录 `logs/` 保留（来自 KAIROS 设计，适合长期运行场景）

## 4. MEMORY.md 索引机制

### 格式

```markdown
- [用户画像](user-profile.md) — 互联网PM，30岁，独居，内向有幽默感
- [沟通偏好](preference-communication-style.md) — 简洁自然，不要总结和说教
- [面试事件](event-job-interview.md) — 2025-06-15大厂终面，跳槽关键机会
- [猫咪饺子](knowledge-cat-dumpling.md) — 橘猫，2023年领养，分离焦虑
```

每行格式：`- [标题](文件名) — 一句话钩子`

- **标题**：人可读的简短名称
- **文件名**：对应的 .md 文件
- **一句话钩子**：描述中最重要的信息点，让 Agent 扫一眼就知道这条记忆值不值得展开看

### 约束

| 指标 | 限制 | 原因 |
|------|------|------|
| 总行数 | ≤ 100 行 | 陪伴 Agent 记忆量远小于代码项目，100 行够用 |
| 单行长度 | ≤ 150 字符 | 防止索引变成内容 |
| 总大小 | ≤ 15 KB | 保证注入系统提示词时不占太多 token |

**与 Claude Code 的差异**：Claude Code 是 200 行 / 25 KB，我们缩减到 100 行 / 15 KB，因为陪伴场景的记忆量远小于代码项目场景。

### 加载时机

MEMORY.md 在以下时刻全量加载到上下文：

1. **Agent 启动时**（首次加载）
2. **每次压缩后**（重新加载，因为压缩会丢失之前的上下文）

加载方式：作为系统提示词的一部分注入，与 Claude Code 通过 `claudemd.ts` 加载 MEMORY.md 的机制一致。

## 5. 会话记忆（Session Memory）

### 5.1 设计理念

会话记忆是**压缩的产物**，是 Agent 在压缩后"醒来"时读到的第一份文件。它回答的核心问题是：

> **"我现在在跟谁聊天？我们最近在聊什么？有什么未完成的事？"**

与 Claude Code 的关键区别：Claude Code 的会话记忆是"任务笔记"（当前在做什么、哪些文件、什么错误），陪伴 Agent 的会话记忆是"关系笔记"（用户近况、聊天脉络、情绪状态）。

### 5.2 模板设计

```markdown
# 今日概览
_<今天的一天一句话总结，含日期>_

# 用户近况
_用户最近在忙什么？情绪状态如何？有什么重要的生活事件在进行中？_

# 活跃话题
_最近在聊什么话题？有没有未讲完的故事、未回答的问题、约好了要继续的事？_

# 关系状态
_跟用户的关系温度如何？最近有没有特别温暖的时刻或者摩擦？沟通节奏如何？_

# 待跟进事项
_有没有用户交代了但还没做的事？提醒？承诺？_

# 重要对话片段
_今天对话中值得保留的具体内容——用户说过的关键原话、做过的决定、分享的故事细节（保持精简，只存最值得保留的）_

# 情绪线索
_今天对话中观察到的用户情绪变化。开心/低落/焦虑/平静？有什么触发了情绪变化？_
```

### 5.3 存储位置

**存入数据库**，而非 .md 文件。原因：

- 压缩时需要快速读写，数据库比文件系统更快
- 需要按时间戳查询历史会话记忆（"昨天我们聊了什么"）
- 与压缩流程紧密耦合，放在同一存储层更内聚

数据库表设计参考：

```sql
CREATE TABLE session_memory (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at  TEXT NOT NULL,     -- ISO 时间戳
    date_key    TEXT NOT NULL,     -- '2025-06-11' 格式，方便按日查询
    content     TEXT NOT NULL,     -- 完整的 Markdown 内容
    token_count INTEGER           -- 大约 token 数，用于预算控制
);
```

### 5.4 大小控制

| 指标 | 限制 |
|------|------|
| 单节上限 | ~1500 token |
| 总计上限 | ~8000 token |

比 Claude Code 的 2000/12000 更紧凑，因为：
- 陪伴对话的信息密度低于编程任务
- 需要给长期记忆的 MEMORY.md 留更多上下文空间

### 5.5 压缩后加载流程

```
每日压缩触发
    │
    ├── 1. 用当前对话生成会话记忆（结构化 Markdown）
    │      → 存入 DB
    │
    ├── 2. 从对话中提取新的长期记忆
    │      → 写 .md 文件
    │      → 更新 MEMORY.md 索引
    │
    ├── 3. 执行压缩（丢弃旧对话，保留压缩摘要）
    │
    └── 4. 压缩后重建上下文：
           ├── 从 DB 加载最新会话记忆 → 注入为 system-reminder
           ├── 重新加载 MEMORY.md → 注入系统提示词
           └── 加载相关的长期记忆文件（见第 6 节）
```

## 6. 每日日志（Daily Log）

### 6.1 设计理念

借鉴 Claude Code KAIROS 模式的日志设计，但适配陪伴场景：

- **Append-only**：只追加，不修改已有条目
- **时间戳子弹点**：每条记录带有精确时间
- **整合阶段回溯**：日志的读者不是 Agent 的实时上下文，而是整合阶段的 Agent

### 6.2 格式

文件路径：`memory/logs/YYYY/MM/YYYY-MM-DD.md`

```markdown
# 2025-06-11 对话日志

- [09:32] 用户早起，说昨晚没睡好，饺子半夜一直在叫
- [09:35] 聊了会失眠的话题，用户说最近压力大
- [14:20] 用户午休来聊了几句，分享了一个搞笑视频
- [22:15] 用户说面试改期了，从6月15改到6月17，因为面试官出差
- [23:40] 用户睡前聊了会，心情比白天好
```

### 6.3 写入时机

在对话过程中，由 Agent **实时追加**。系统提示词中明确指示：

```
As you converse, record anything worth remembering by appending to today's
daily log file: memory/logs/YYYY/MM/YYYY-MM-DD.md

Write each entry as a short timestamped bullet. Create the file (and parent
directories) on first write if it does not exist. Do not rewrite or reorganize
the log — it is append-only.

What to log:
- User's mood changes and emotional state
- Important things the user shared about their life
- Commitments and follow-ups mentioned
- Anything the user explicitly asks you to remember
- Key decisions or changes in plans
```

**与 Claude Code 的差异**：Claude Code 的日志只在 KAIROS（助手模式）下启用。我们默认启用，因为长期运行场景天然适合日志流。

### 6.4 日志与整合的关系

日志是整合的输入源。整合 Agent 在"第二阶段——采集"时读取近期日志，从中提取值得永久保留的信息写入长期记忆。

## 7. 记忆提取：时机与策略

### 7.1 提取时机

Claude Code 有两种提取路径：主 Agent 实时写 + 后台 Agent 每轮提取。对于 24/7 陪伴 Agent，我们**只在压缩时提取**：

```
┌──────────────────────────────────────────────┐
│             实时对话（不提取）                  │
│                                              │
│   用户说话 → Agent回复 → 用户说话 → Agent回复  │
│   ...                                        │
│   Agent 追加日志条目（轻量，不影响对话流）       │
│                                              │
├──────────────────────────────────────────────┤
│            压缩窗口到达（闲时）                  │
│                                              │
│   ① 生成会话记忆 → 存 DB                      │
│   ② 提取长期记忆 → 写 .md + 更新 MEMORY.md    │
│   ③ 执行压缩                                  │
│   ④ 重建上下文                                │
└──────────────────────────────────────────────┘
```

**为什么不每轮提取？**
- 24/7 Agent 对话频率高，每轮提取成本不可接受
- 压缩是唯一"会丢失上下文"的时刻，在此之前对话历史都在上下文窗口里，不需要记忆系统来补偿
- 用户说"记住这个"时，Agent 可以直接写记忆文件（即时保存），不需要后台提取

### 7.2 提取策略

提取 Agent 在压缩时同时做两件事：

**① 生成会话记忆**（优先级最高）

```
你正在对今天的对话进行压缩。请生成一份结构化的会话记忆笔记。

按照以下模板填写：
{{session_memory_template}}

要求：
- "今日概览"必须包含日期和一句话总结
- "用户近况"是压缩后 Agent 重新"醒来"时最重要的锚点
- "活跃话题"中的未完成事项决定了压缩后第一句话该说什么
- "重要对话片段"只保留最值得的 3-5 条，不要变成对话日志
- "情绪线索"帮助 Agent 理解当前该用什么语气
```

**② 提取长期记忆**（增量提取）

```
同时，检查今天对话中是否有值得长期记住的信息。

现有长期记忆清单：
{{memory_manifest}}

对每条新信息：
1. 如果已有对应记忆文件 → 更新它
2. 如果是全新的 → 创建新记忆文件
3. 如果不确定值不值得长期记住 → 不存

按以下类型选择：
- user：关于用户身份、性格、生活状况的新信息
- preference：用户对 Agent 行为的纠正或确认
- event：用户生活中发生的重要事件
- knowledge：用户希望你记住的零散事实

不要存：
- 临时情绪（属于会话记忆）
- 闲聊细节（属于日志）
- 能从已有记忆推导的信息
```

### 7.3 用户主动保存

当用户说"记住这个"、"忘了那个"时，Agent 立即执行：

- **记住**：写记忆文件 → 更新 MEMORY.md → 回复"已记住"
- **忘记**：找到对应记忆文件 → 删除 → 从 MEMORY.md 移除 → 回复"已忘记"

这不需要等压缩窗口，是即时操作。

## 8. 记忆检索机制

### 8.1 两级检索

与 Claude Code 一致的两级检索，但更轻量：

**第一级：MEMORY.md 全量扫描**

压缩后，MEMORY.md 作为系统提示词的一部分被加载。Agent 扫一眼就知道有哪些记忆可用。

**第二级：相关记忆按需加载**

当用户提到某个话题时，检查 MEMORY.md 中是否有相关条目。如果有，读取对应 .md 文件全文注入上下文。

### 8.2 触发规则

不需要像 Claude Code 那样用 Sonnet 子 Agent 做相关性选择。陪伴场景的记忆量小、语义关联直接，可以用更简单的规则：

```
当用户消息满足以下任一条件时，加载相关记忆：
1. 用户提到 MEMORY.md 索引条目中的关键词
2. 用户提到的人名/地名/事件名与某条记忆的 name 或 description 匹配
3. 用户说"你还记得..."、"之前说的..."等回忆性短语
4. 用户说"记住这个"、"忘了那个"等记忆操作短语
```

实现方式：对 MEMORY.md 的每一行做简单的关键词/子串匹配即可。如果后续记忆量增长到 50+ 条，可以引入嵌入向量检索。

### 8.3 已加载记忆去重

维护一个 `already_loaded` 集合，避免同一轮对话中重复加载同一记忆文件。

### 8.4 记忆加载上限

| 指标 | 限制 |
|------|------|
| 单次加载记忆数 | ≤ 3 条 |
| 每条记忆上限 | ≤ 1000 token |
| 单次加载总 token | ≤ 3000 token |

比 Claude Code 的 5 条更保守，因为陪伴 Agent 的上下文预算更紧张（需要更多空间给对话本身）。

## 9. 记忆整合与修剪

### 9.1 整合时机

整合（Dream）是比每日压缩更重的操作，不应每次压缩都做。建议：

```
整合触发条件（全部满足）：
1. 距上次整合 ≥ 3 天
2. 距上次整合后有 ≥ 3 次压缩（即 3 天的对话量）
3. 当前处于闲时窗口
```

### 9.2 整合流程

借鉴 Claude Code autoDream 的四阶段设计，适配陪伴场景：

```
## Phase 1 — 定向
- 读取 MEMORY.md 了解当前记忆格局
- 扫描记忆文件列表，感知哪些文件存在

## Phase 2 — 采集
- 读取近期每日日志（logs/ 目录下最近 3-7 天）
- 读取近期会话记忆（DB 中最近 3 条）
- 检查是否有记忆与当前已知信息矛盾

## Phase 3 — 整合
- 合并近义记忆（如 "用户喜欢猫" 和 "用户养了只橘猫" → 合并为一条）
- 将相对日期转为绝对日期（"下周" → "2025-06-18"）
- 删除已被推翻的事实（面试已结束 → 更新事件记忆为结果）
- 已完成的事件标记为归档状态（在 frontmatter 中 updated 字段反映）

## Phase 4 — 修剪
- 更新 MEMORY.md 保持在 100 行 / 15KB 以内
- 移除指向已删除/归档记忆的索引行
- 精简过长的索引条目
```

### 9.3 事件记忆的生命周期

事件记忆有天然的生命周期：

```
新建 → 进行中 → 已结束 → 归档/删除
  ↑                                    ↓
  └──── 用户后续又提到此事 ←────────────┘
```

整合时对事件记忆的处理规则：
- **进行中**：保留，更新进展
- **已结束且超过 7 天**：删除文件和索引（信息已沉淀为 user/knowledge 类型记忆）
- **已结束但 7 天内**：保留，标记为 `status: concluded`，下次整合再删
- **用户后来又提起**：升级回 `status: active`

## 10. 记忆新鲜度与信任

### 10.1 新鲜度标注

对超过 7 天未更新的记忆，在加载时追加新鲜度提示：

```
<system-reminder>
这条记忆已 12 天未更新，信息可能已过时。
如果用户提到相关话题，先确认当前情况再引用。
</system-reminder>
```

**与 Claude Code 的差异**：Claude Code 用 1 天阈值。陪伴场景的信息变化更慢（用户性格不会一天一变），7 天更合理。但事件类记忆用 3 天阈值（事件进展变化快）。

### 10.2 验证原则

```
记忆说的是"当时"的情况，不代表"现在"还是这样。

- 如果记忆提到某事件"即将发生" → 先问"那个面试怎么样了"
- 如果记忆提到某种偏好 → 用户现在的行为如果与之矛盾，信现在
- 如果记忆提到某个人 → 不确定关系是否还一样，不要想当然
```

### 10.3 冲突处理

当记忆与当前对话中的信息冲突时：

```
信任当前对话中的信息 > 信任记忆

冲突时：
1. 以当前对话为准
2. 更新或删除冲突的记忆
3. 不要对用户说"我记得你之前说的不一样"——直接接受新信息即可
```

## 11. 系统提示词中的记忆指令

以下是注入系统提示词的完整记忆指令文本（可直接使用）：

```markdown
# 记忆系统

你有一个持久化的文件记忆系统，位于 `memory/` 目录。

你应当逐步积累这个记忆系统，让未来的自己（压缩后重新醒来时）能够完整了解用户是谁、
你应该如何陪伴、关系中发生了什么重要的事。

## 记忆类型

<types>
<type>
    <name>user</name>
    <description>关于用户身份、性格、处境的信息。帮你理解对方是谁，该如何与 ta 相处。</description>
    <when_to_save>了解到用户的身份、性格、生活状况时</when_to_save>
    <examples>
    用户：我其实挺社恐的，不太喜欢跟同事一起吃饭
    → [保存 user 记忆：用户社恐，不喜欢社交应酬]
    </examples>
</type>
<type>
    <name>preference</name>
    <description>用户对你的行为方式的指导——纠正和确认都要记。不只要记挨骂，还要记被夸。</description>
    <when_to_save>用户纠正你的行为，或者确认"就是这样没错"时。必须包含 Why 和 How to apply。</when_to_save>
    <examples>
    用户：你别每次都"总结一下"，看着好烦
    → [保存 preference 记忆：不要总结式结尾。Why: 用户觉得烦。How to apply: 说完就停]
    </examples>
</type>
<type>
    <name>event</name>
    <description>用户生活中的重要事件——里程碑、变故、计划、待办。这些都是有时间性的。</description>
    <when_to_save>用户提到生活中发生了什么重要的事，或将要有重要的事。相对日期转绝对日期。</when_to_save>
    <examples>
    用户：下周二有个很重要的面试
    → [保存 event 记忆：2025-06-17 有重要面试。Why: 用户很看重这次机会]
    </examples>
</type>
<type>
    <name>knowledge</name>
    <description>用户希望你记住的零散事实——人名、习惯、喜好、只有你们之间懂的梗。</description>
    <when_to_save>用户说"记住这个"，或反复提到某个主题时</when_to_save>
    <examples>
    用户：饺子（我家猫）最喜欢追激光笔
    → [保存 knowledge 记忆：用户的猫饺子喜欢追激光笔]
    </examples>
</type>
</types>

## 什么不要存

- 临时情绪和心情 → 这些会在会话记忆中处理
- 闲聊的具体内容 → 日志里记录即可
- 能从已有记忆推导的信息
- 任何用户说"忘了这个"的内容 → 立即删除

## 如何保存记忆

保存记忆是两步操作：

**第一步** — 将记忆写入独立文件（如 `user-profile.md`），使用以下格式：

```markdown
---
name: {{记忆名称}}
description: {{一句话描述，越具体越好——检索时靠这个}}
type: {{user, preference, event, knowledge}}
created: {{ISO日期}}
updated: {{ISO日期}}
---

{{正文内容}}

{{preference/event 类型追加：}}
**Why:** {{为什么重要}}
**How to apply:** {{什么场景该想起这条}}
```

**第二步** — 在 `MEMORY.md` 中添加一行索引：
`- [标题](文件名.md) — 一句话钩子`

`MEMORY.md` 是索引，不是记忆——不要把内容写进索引。索引最多 100 行。

- 先检查有没有可以更新的已有记忆，再考虑新建
- 记忆按主题组织，不按时间
- 过时或错误的记忆要及时更新或删除

## 何时读取记忆

- MEMORY.md 始终在你的上下文中——扫一眼就知道有哪些记忆
- 当用户提到某个话题，而 MEMORY.md 中有相关条目时，读取对应的记忆文件
- 用户说"你还记得..."时，必须检索相关记忆
- 用户说"忘了/不要用"某条记忆时，当作这条记忆不存在

## 推荐前先验证

记忆是"当时"的快照，不代表现在还是这样。

- 如果记忆说某事件"即将发生"，先问进展
- 如果记忆说用户有某种偏好，但用户现在的行为与之矛盾，信现在
- 不要引用过时的信息当作事实

## 日志

对话过程中，将重要时刻追加到今日日志：
`memory/logs/YYYY/MM/YYYY-MM-DD.md`

每条日志是一个简短的时间戳条目。日志只追加不修改。
```

## 12. 完整数据流

### 12.1 日常对话流

```
用户发消息
    │
    ├── Agent 检查是否需要加载相关记忆
    │   └── 关键词匹配 MEMORY.md → 按需加载 .md 文件
    │
    ├── Agent 回复
    │
    ├── Agent 追加日志条目（append-only，不阻塞对话）
    │
    └── 如果用户说"记住/忘了"→ 立即写/删记忆文件 + 更新索引
```

### 12.2 压缩窗口流

```
闲时窗口到达
    │
    ├── 1. 提取 Agent 读取当日完整对话
    │
    ├── 2. 生成会话记忆（结构化 Markdown）
    │   └── 存入 DB（session_memory 表）
    │
    ├── 3. 提取长期记忆（增量）
    │   ├── 扫描现有记忆清单
    │   ├── 从对话中识别新的 user/preference/event/knowledge
    │   ├── 写 .md 文件 / 更新已有 .md 文件
    │   └── 更新 MEMORY.md 索引
    │
    ├── 4. 执行上下文压缩
    │   └── 丢弃旧对话，保留压缩摘要
    │
    └── 5. 重建上下文
        ├── 从 DB 加载最新会话记忆 → system-reminder
        ├── 重新加载 MEMORY.md → 系统提示词
        └── 加载当前活跃话题相关的记忆文件
```

### 12.3 整合流

```
整合条件满足（3天 + 3次压缩 + 闲时）
    │
    ├── Phase 1: 读取 MEMORY.md + 记忆文件列表
    │
    ├── Phase 2: 读取近期日志 + 近期会话记忆
    │
    ├── Phase 3: 合并近义记忆、转换日期、删除过时信息
    │
    └── Phase 4: 修剪 MEMORY.md（≤100行/15KB）
```

## 13. 与 Claude Code 设计的关键差异

| 维度 | Claude Code | 本设计 | 原因 |
|------|------------|--------|------|
| 记忆类型 | user/feedback/project/reference | user/preference/event/knowledge | 面向人与关系，不面向代码与项目 |
| 提取时机 | 每轮对话后 | 仅压缩时 | 24/7 不需要跨会话恢复，只在压缩时补偿 |
| 会话记忆 | 10节编程模板 | 7节陪伴模板 | 陪伴场景关注情绪/关系/话题，不关注文件/错误 |
| 团队记忆 | 有 | 无 | 单用户私人场景 |
| 记忆索引 | 200行/25KB | 100行/15KB | 记忆量更小 |
| 新鲜度阈值 | 1天 | 7天（事件3天） | 人的信息比代码变化更慢 |
| 日志模式 | 仅KAIROS模式 | 默认启用 | 长期运行天然适合日志 |
| 整合频率 | 24h+5会话 | 3天+3次压缩 | 降低频率，陪伴Agent更关注稳定 |
| 检索方式 | Sonnet子Agent | 关键词匹配 | 记忆量小，不需要重型检索 |
| 路径结构 | 按git root隔离 | 固定memory/目录 | 无项目概念 |

## 14. 实现优先级建议

### P0：最小可用

1. 记忆文件格式 + MEMORY.md 索引
2. 系统提示词中的记忆指令（第 11 节）
3. 用户主动保存/删除（"记住这个"/"忘了那个"）
4. 压缩时生成会话记忆 → 存 DB
5. 压缩后重新加载 MEMORY.md + 会话记忆

### P1：核心闭环

6. 压缩时提取长期记忆（写 .md + 更新 MEMORY.md）
7. 每日日志（append-only）
8. 相关记忆按需加载
9. 新鲜度标注

### P2：长期维护

10. 记忆整合（Dream）
11. 事件记忆生命周期管理
12. 记忆统计与监控（记忆总数、命中率、平均年龄）
13. 如记忆增长到 50+ 条，引入嵌入向量检索

---

*本设计基于 Claude Code 源码的逆向分析，保留了其核心设计精华（两级检索、索引内容分离、不信任记忆、封闭分类法），并针对 24/7 陪伴场景做了四项关键适配：记忆类型面向人与关系、提取时机改为仅压缩时、会话记忆模板改为陪伴导向、检索方式简化为关键词匹配。*
