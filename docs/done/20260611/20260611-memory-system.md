- 自动压缩与后台一键压缩共用同一流程；
- 管理后台支持查看、单条删除和一键清除长期记忆；

- 全量测试通过：149 项。

## 一、设计目标

记忆系统只记住真正值得长期记住的内容。

设计时优先保证：

- 会话在每日压缩后仍然连续；
- 长期记忆少而准确，不把聊天流水沉淀为用户画像；
- 无法确定是否值得长期保存时，先留在每日摘要中观察；
- 每项重要决策同时记录未选择的方案与原因，避免重复讨论。

## 二、记忆分层与职责

### 1. 当天记忆：原始对话

- 载体：`ConversationContext` 中未经加工的历史消息。
- 职责：保留当天完整对话，保证当前交流的连贯性。
- 生命周期：持续存在，直到每日 Compact 淘汰旧上下文。
- 特征：信息最完整，但会占用上下文窗口。

### 2. 跨天记忆：每日摘要

- 载体：每日 Compact 生成并持久化的结构化摘要。
- 职责：像日志一样记录当天发生了什么，使下一天能够延续近期话题、状态和未完成事项。
- 加载规则：新一天默认携带前一天摘要；更早的每日摘要按需读取。
- 特征：允许包含短期、会变化的信息，不等同于长期事实。

这里不再额外建立一套独立的 Session Memory。现有 Compact 是压缩动作，它生成的每日摘要就是本项目的跨天会话记忆。

### 3. 长期记忆：稳定认知

- 载体：`MEMORY.md` 索引 + 独立 Markdown 记忆文件。
- 职责：保存未来仍必须知道、不能只依赖每日摘要恢复的信息。
- 特征：数量少、变化少、需要长期维护；信息变化后应更新或删除。

一句话区分：

> 原始对话记录“说过什么”，每日摘要记录“最近发生了什么”，长期记忆记录“以后仍必须知道什么”。

提醒、待办和定时任务属于行动状态，不属于长期记忆。

## 三、长期记忆准入标准

用户明确要求“记住”时，直接满足准入条件。

Agent 自主判断时，信息必须具有长期价值，并至少满足以下一项：

1. 很少变化，或者变化后必须更新；
2. 无法从近期对话或每日摘要中可靠推导；
3. 忘记后会导致明显误解用户；
4. 忘记后会破坏关系连续性；
5. 忘记后会迫使用户重复解释重要背景。

“重要”不作为独立标准，因为它过于主观。重要性由上述可观察后果定义。

保守原则：

> 不确定是否值得长期保存时，不写入长期记忆，先保留在每日摘要中；后续反复出现或价值变得明确时再晋升。

## 四、长期记忆写入时机

长期记忆有两条写入路径：

### 1. 用户明确要求：即时写入

用户明确要求记住某件事时，Agent 在当前对话中立即保存，避免信息在每日压缩前丢失。

### 2. Agent 自主判断：每日压缩时审查

每日 Compact 读取当天完整对话，并在生成跨天摘要的同时审查是否出现符合准入标准的新增长期记忆。

即使当天已有用户明确要求并即时写入的记忆，Compact 仍需审查当天其他内容。审查前必须读取现有长期记忆，避免重复创建，并允许更新已有记忆或处理冲突。

最终规则：

> 用户指定即时写入；每日压缩进行全量增量审查。

## 五、长期记忆存储与读取

采用类似 Claude Code 的“目录 + 章节”结构：

```text
memory/
├── MEMORY.md
├── <memory-name>.md
├── <memory-name>.md
└── ...
```

### `MEMORY.md`

- 是目录，不是正文；
- 每条只包含文件链接、标题和一句话摘要；
- 不在索引中堆放记忆细节；
- 上限暂定 200 行，超限时截断并产生维护警告。

### 独立记忆文件

- 每条记忆对应一个 Markdown 文件；
- 文件名使用稳定、简短、可读的标识；
- 正文保存完整背景以及必要的更新时间；
- Agent 根据当前话题按需读取正文。

### 两级读取

第一级：全量加载 `MEMORY.md`，让 Agent 知道有哪些长期记忆可用。

由于本项目会话长期不中断，加载时机调整为：

- Agent 启动或上下文首次构建时；
- 每日 Compact 完成并重建上下文时。

第二级：Agent 根据当前话题，从目录判断并按需读取相关记忆文件正文。同一上下文周期内避免重复加载同一文件。

长期记忆数量较少时，由主 Agent 自行判断相关性，不单独启动子 Agent。未来只有在记忆规模和检索误差证明有需要时，再引入专门的相关性筛选。

## 六、当前不做长期记忆分类

当前不预设 `user`、`relationship`、`knowledge` 等固定分类。

原因：

- 预计长期记忆数量很少；
- 当前核心问题是判断“是否值得记”，不是决定标签；
- 分类会增加 Agent 写入时的决策负担；
- 尚无真实记忆数据证明检索、维护或遗忘需要按类别处理。

后续如果实际数据表明不同记忆需要不同的加载、更新或遗忘规则，再从真实需求中建立分类。

## 七、已否决或暂缓的方案

### 1. 将 Compact 与 Session Memory 设计成两套机制

**决定：否决。**

现有 Compact 已负责生成每日摘要；该摘要能够承担跨天会话记忆。再建立独立 Session Memory 会造成职责重叠。

### 2. 为统一格式而把每日摘要从数据库迁移为 Markdown

**决定：暂不采用。**

存储格式统一不是目标。每日摘要与长期记忆职责不同，可以分别使用数据库和 Markdown。除非后续出现明确的查询、迁移或维护问题，否则不改现有 Compact 存储。

### 3. 一开始就建立长期记忆分类体系

**决定：暂不采用。**

先使用统一准入标准积累少量真实记忆，再根据真实检索和维护问题决定是否分类。

### 4. Agent 在每轮对话后自主提取长期记忆

**决定：否决。**

每轮提取成本高，也容易把暂时情绪和聊天细节过早固化。Agent 自主提取集中在每日 Compact；只有用户明确要求时才即时写入。

### 5. 只使用文件名作为索引

**决定：否决。**

文件名不足以表达记忆内容。使用 `MEMORY.md` 保存标题和一句话摘要，文件名只作为稳定定位符。

### 6. 立即引入子 Agent 进行相关记忆筛选

**决定：暂缓。**

记忆数量较少时，主 Agent 可根据 `MEMORY.md` 自行按需读取。达到实际规模瓶颈后再考虑子 Agent、嵌入或其他检索机制。

### 7. 将提醒和待办作为长期记忆

**决定：否决。**

提醒和待办是需要执行和改变状态的行动数据，应由提醒或任务系统管理；长期记忆只负责认知连续性。

## 八、工具设计

### 1. 设计选择

采用一个受限的 `memory` 文件工具，参考 Anthropic Memory Tool 的命令式设计。

不拆分为 `read_memory`、`create_memory`、`update_memory`、`delete_memory` 多个工具，避免增加模型选择歧义。也不暴露通用文件系统工具；`memory` 只能访问当前用户的长期记忆目录。

第一版支持以下命令：

| 命令 | 职责 |
|------|------|
| `view` | 查看 `MEMORY.md`、单条记忆文件或允许的目录列表 |
| `create` | 创建新的 Markdown 记忆文件 |
| `str_replace` | 对已有记忆文件执行精确文本替换 |

第一版暂不支持：

- `insert`：容易依赖不稳定的行号，现阶段可由 `str_replace` 完成必要更新；
- `rename`：会同时影响文件路径和 `MEMORY.md` 链接，第一版没有必要承担该复杂度；
- 任意路径的文件读写；
- 递归删除目录。

建议的 Anthropic 工具定义外形：

```json
{
  "name": "memory",
  "description": "Read and maintain persistent long-term memory files for the current user. Use this tool to inspect a relevant memory, create a memory the user explicitly asked to preserve, or update an existing memory when facts change. Deletion is not available to the model.",
  "input_schema": {
    "type": "object",
    "properties": {
      "command": {
        "type": "string",
        "enum": ["view", "create", "str_replace"]
      },
      "path": {
        "type": "string",
        "description": "Path relative to the current user's memory directory."
      },
      "file_text": {
        "type": "string",
        "description": "Complete initial file content. Required only for create."
      },
      "old_str": {
        "type": "string",
        "description": "Exact text to replace. Required only for str_replace and must occur exactly once."
      },
      "new_str": {
        "type": "string",
        "description": "Replacement text. Required only for str_replace."
      }
    },
    "required": ["command", "path"]
  }
}
```

实际注册时应使用项目现有的 Anthropic 工具定义结构，并为各命令补充详细使用条件、禁止场景和输入示例。

### 2. `MEMORY.md` 的维护责任

第一版由 Agent 维护 `MEMORY.md`：

1. 创建记忆正文；
2. 再更新 `MEMORY.md`，加入标题、文件链接和一句话摘要；
3. 更新正文后，必要时同步修改索引摘要；
4. 模型不负责删除；管理端删除正文时由文件服务同步移除索引项。

系统不替 Agent 判断摘要内容，也不自动重建索引。系统负责校验路径、文件类型、大小和操作合法性，并将不一致暴露为可诊断错误。

选择这一方案是为了贴近 Claude Code 的文件记忆模型，先观察真实运行中的错误类型。若实际出现频繁漏同步，再将索引维护升级为系统事务，而不是预先实现复杂的业务层。

### 3. 工程默认值

以下属于可调整的工程默认值，不改变产品语义：

| 项目 | 第一版默认值 |
|------|--------------|
| 可访问范围 | 当前用户专属记忆目录 |
| 路径形式 | 相对于记忆目录的路径，禁止绝对路径 |
| 路径安全 | 解析规范路径后验证仍位于记忆根目录；拒绝 `..` 等目录穿越 |
| 文件类型 | 仅允许 `.md` |
| `MEMORY.md` | 允许 `view` 和 `str_replace`；模型无删除命令 |
| 创建冲突 | 文件已存在时返回错误，不覆盖 |
| 精确替换 | `old_str` 必须且只能出现一次，否则不修改并返回错误 |
| 删除 | 仅管理后台可删除主题文件，不允许删除目录或 `MEMORY.md` |
| 写入方式 | 临时文件写入完成后原子替换目标文件 |
| 并发 | 同一用户的记忆写操作串行执行 |
| 工具结果 | 返回稳定的操作状态、相对路径和明确错误原因，不返回无关内容 |

文件大小和工具返回内容上限在实现前结合现有上下文预算确定，并作为集中配置或常量保留，不能散落为无法追踪的魔法数字。

### 4. 可观测性与问题定位

所有默认值都必须能够从日志或 trace 中定位，不能静默失败。

每次 `memory` 工具调用至少记录：

- `user_id` 的安全标识；
- `command`；
- Agent 提交的相对路径；
- 系统解析后的规范化相对路径；
- 成功或失败状态；
- 稳定错误码与人类可读错误原因；
- 读写字节数；
- 调用来源：普通对话即时写入或每日 Compact 审查。

不在普通日志中记录完整记忆正文，避免泄漏用户隐私。完整工具输入和结果是否进入现有 `llm_traces`，沿用项目当前的 trace 策略，并在管理界面或日志中能够按 `turn_id` / `call_id` 关联。

建议第一版使用稳定错误码，例如：

- `memory_invalid_path`
- `memory_path_escape`
- `memory_not_found`
- `memory_already_exists`
- `memory_ambiguous_replace`
- `memory_file_too_large`
- `memory_index_protected`
- `memory_io_error`

因此，当默认值不合理或工具行为出错时，可以根据 trace 提供具体调用、路径、错误码和预期行为，再针对性调整限制或实现。

### 5. 普通对话与 Compact 的复用边界

普通对话中的用户明确记忆请求与每日 Compact 的自主审查，共用同一套底层记忆文件服务、权限校验、并发控制和日志记录。

模型入口采用不同方式：

- 普通对话：向主 Agent 暴露 `memory` 工具，由 Agent 在用户明确要求时即时调用；
- 每日 Compact：不开放模型工具调用，而是要求压缩模型在一次响应中同时输出摘要与结构化的记忆变更计划，再由 runtime 调用同一底层记忆文件服务批量执行。

底层能力复用，模型交互形式不强求一致。

## 九、Compact 与长期记忆的集成决策

### 1. 现有调用链结论

当前 Compact 是一条单次文本调用链：

1. 在 `/chat` 的用户级锁内、正式聊天 turn 开始前触发；
2. 从 `ConversationContext` 取得完整历史；
3. 过滤旧 `<summary>`；
4. 追加压缩提示词；
5. 发起一次非流式 LLM 调用，明确禁止工具；
6. 从响应中提取 `<summary>`；
7. 用摘要替换内存历史；
8. 将旧 `raw_events` 软删除并写入压缩状态；
9. 单独保存一份每日摘要。

当前 `compress_conversation()` 只返回摘要字符串，没有工具循环、工具结果回填或多步完成协议。普通聊天的工具循环则位于 `ChatAgent` 内，与 Compact 是两条独立路径。

### 2. 拍板方案

> Compact 输出结构化记忆变更计划，由 runtime 校验并执行；Compact 模型不直接调用 `memory` 工具。

原因：

- 不需要复制 `ChatAgent` 的多步工具循环；
- 一次模型调用即可同时完成“跨天摘要”和“长期记忆审查”；
- runtime 可以在文件落盘前统一校验路径、操作类型、准入理由和索引同步；
- 可以将多个文件变化作为一个批次处理，避免模型执行到一半中断；
- 摘要生成与记忆执行的成功状态可以分别记录；
- 更容易测试和重放，不依赖模型连续正确调用多次工具。

### 3. Compact 输出契约

第一版仍采用可明确解析的单次响应。概念结构如下：

```json
{
  "summary": "用于替换当天原始历史的跨天摘要",
  "memory_operations": [
    {
      "command": "create | str_replace",
      "path": "相对于当前用户记忆目录的 Markdown 文件路径",
      "file_text": "create 使用",
      "old_str": "str_replace 使用",
      "new_str": "str_replace 使用",
      "reason": "为什么该变化满足长期记忆准入标准"
    }
  ]
}
```

实际实现时优先使用 provider 已支持且测试可靠的结构化输出方式。如果 `json_object` 在当前 DeepSeek Anthropic 兼容端点不稳定，则保留现有文本响应模式，使用严格的标记块分别承载摘要和 JSON 操作列表。

`memory_operations` 可以为空。没有符合准入标准的长期记忆时，必须返回空数组，不能为了完成任务而强行创建记忆。

### 4. 执行顺序

runtime 按以下顺序处理：

1. 解析并校验 Compact 响应；
2. 确认摘要合法；
3. 校验全部记忆操作，不立即修改文件；
4. 将记忆操作作为一个批次执行；
5. 批次成功后，再替换 `ConversationContext` 并持久化压缩状态；
6. 保存每日摘要；
7. 记录 Compact 与记忆批次的执行结果。

记忆批次必须支持回滚：任一操作失败时，恢复本批次已修改的文件，不能留下只创建正文但未更新索引等半完成状态。

### 5. 失败策略

- 摘要无法解析：不压缩，不执行记忆操作；
- 任一记忆操作格式非法：不执行整个记忆批次，不压缩；
- 记忆批次执行失败：回滚文件，不压缩；
- 记忆操作为空且摘要合法：正常压缩；
- 压缩 DB 持久化失败：记录高优先级错误；实现时需确保内存历史不会永久领先于持久化状态；
- 手动 Compact 与自动 Compact 使用相同流程，避免两套行为。

这里选择“失败时不淘汰原始历史”，因为原始历史一旦软删除，尚未成功沉淀的长期记忆可能无法可靠恢复。错误必须进入日志和 trace，便于修复后重新触发 Compact。

### 6. 不采用 Compact 直接工具调用

**决定：否决。**

直接工具调用需要为 Compact 新建多轮模型循环、生成 `tool_result`、限制最大步数并处理“工具已经写入但摘要最终失败”等状态。它会把一次确定性的后台压缩变成另一套 Agent runtime，当前收益不足以覆盖复杂度和失败风险。

## 十、记忆文件与 Compact 格式

### 1. 记忆文件粒度

采用“一个主题一个文件”，不采用“一个事实一个文件”。

示例：

```text
memory/
├── MEMORY.md
├── user-background.md
├── mother-relationship.md
└── communication-under-stress.md
```

同一主题下的相关事实放在一个文件中维护。只有当主题之间的读取场景、更新频率或内容边界明显不同，才拆成多个文件。

这样可以避免长期记忆被切成大量零碎文件，也方便 Agent 在需要时一次读取完整背景。

### 2. 正文格式

第一版使用普通 Markdown，不使用 YAML frontmatter。

推荐格式：

```markdown
# 与母亲的关系

更新时间：2026-06-11

用户与母亲联系密切，但谈到婚姻时容易发生压力和冲突。
母亲经常催婚，用户不希望 Agent 简单劝用户顺从。
```

最低要求：

- 第一行是主题标题；
- 包含最后更新时间；
- 正文只维护当前有效认知；
- 内容应能脱离原始对话独立理解；
- 不保存普通聊天流水和无关原话。

格式保持简单，不强制拆成 `Why`、`How to apply` 等固定字段。若某个主题确实需要说明使用边界，可以在正文中自然增加小标题。

### 3. 更新语义

记忆文件维护“当前有效认知”，不在正文中保留修改历史。

当新信息推翻旧信息时，直接更新对应内容与更新时间。历史变化过程仍可从每日摘要中查询，不在长期记忆文件中重复保存。

删除的内容不使用删除线或“旧值 -> 新值”长期堆积，避免 Agent 读取时混淆当前事实与过期事实。

### 4. `MEMORY.md` 固定格式

`MEMORY.md` 每条索引使用一行：

```markdown
- [与母亲的关系](mother-relationship.md) - 联系密切，但催婚话题容易造成压力和冲突
```

约束：

- 每条只包含标题、相对文件链接和一句话摘要；
- 一条索引占一行；
- 摘要描述“什么时候可能需要读取”，不展开正文细节；
- 文件名使用稳定、简短、可读的英文 kebab-case；
- `MEMORY.md` 不使用分类章节，第一版保持扁平列表；
- 总计不超过 200 行。

完整示例：

```markdown
# 长期记忆索引

- [用户长期背景](user-background.md) - 用户的稳定身份、生活背景与长期处境
- [与母亲的关系](mother-relationship.md) - 联系密切，但催婚话题容易造成压力和冲突
- [压力下的沟通方式](communication-under-stress.md) - 用户压力大时更希望先被理解，不要立即给建议
```

### 5. Compact 的内容与存储

每日 Compact 的摘要继续使用结构化 Markdown 文本，并继续存入现有数据库。

不将每日摘要迁移为 `.md` 文件，也不为了和长期记忆统一而修改现有存储介质：

- 每日摘要是按日期查询的跨天日志，数据库适合覆盖写入和历史查询；
- 长期记忆是按主题维护、供 Agent 按需读取的稳定认知，Markdown 文件适合审计和编辑；
- 两者都可以使用 Markdown 作为内容格式，但不要求使用相同的存储方式。

Compact 的单次模型响应中：

- `summary`：结构化 Markdown；
- `memory_operations`：JSON 数组；
- runtime 将摘要存入数据库，将通过校验的记忆变化写入 Markdown 文件。

### 6. 已否决方案

#### 一个事实一个文件

**决定：否决。**

会产生大量零碎文件，使索引膨胀，并让 Agent 为理解一个主题反复读取多个文件。

#### 第一版使用 YAML frontmatter

**决定：暂不采用。**

当前没有分类筛选、复杂元数据查询或外部索引器需求。标题和更新时间写在普通 Markdown 中已经足够；frontmatter 只会增加生成和解析约束。

#### 在长期记忆正文保留变更历史

**决定：否决。**

长期记忆用于提供当前认知，混入过期事实会增加误用风险。变化历史由每日摘要保留。

#### 将每日摘要迁移为 Markdown 文件

**决定：否决。**

内容格式与存储介质无需统一。现有数据库已经满足每日摘要的日期检索和持久化职责，迁移没有明确收益。

#### 给 `MEMORY.md` 预设分类章节

**决定：暂不采用。**

当前长期记忆数量预计很少，也尚未建立分类体系。先使用扁平索引，根据真实规模和使用数据再决定是否分组。

## 十一、记忆权限与管理

### 1. Compact 批量操作

- 一次 Compact 最多操作 3 个主题文件；
- 允许 `create` 和 `str_replace`；
- 所有操作作为一个原子批次执行；
- 任一操作校验或执行失败时回滚整个批次，并且不淘汰原始对话。

### 2. 模型权限

模型负责：

- 用户明确要求记住时立即创建或更新记忆；
- 每日 Compact 时自主审查并创建或更新记忆；
- 当前对话出现明确新事实时修正已有记忆。

模型不能删除记忆：

- 普通对话不向模型开放 `delete`；
- Compact 变更计划不允许 `delete`；
- 用户在对话中说“忘记”不触发模型删除流程。

用户明确要求记住时直接保存。本项目由用户本人使用，不额外设置敏感信息拒绝、二次确认或重要性复核。

### 3. 记忆不可信原则

长期记忆是过去某个时刻形成的认知，不代表现在仍然成立。

信息优先级：

> 当前对话中的明确新信息 > 长期记忆 > 历史每日摘要

处理规则：

- 当前信息与记忆明确冲突时，以当前信息为准并更新记忆；
- 冲突不明确时，不使用旧记忆反驳用户，也不仓促改写记忆；
- 模糊变化先保留在每日摘要中，等待后续明确；
- Agent 引用可能变化的旧记忆时，应将其视为背景而不是绝对事实。

### 4. 用户删除与管理界面

删除权只属于用户，通过管理界面执行。

管理界面需要支持：

- 查看 `MEMORY.md` 索引；
- 查看单条记忆文件正文；
- 选择并删除单条记忆；
- 删除正文时同步删除 `MEMORY.md` 中的索引项；
- 一键清除全部长期记忆。

删除操作必须调用与模型写入相同的底层记忆文件服务，沿用路径校验、原子写入、并发控制和日志记录，不能由前端直接操作文件。

### 5. 一键清除

现有“一键清除”功能必须扩展为同时清除：

- 当前对话内存；
- 对话、摘要及相关运行时持久化数据；
- 当前用户的 `MEMORY.md`；
- 当前用户的所有长期记忆正文文件。

清除后保留当前项目原本规定不能删除的微信联系人绑定信息。清除动作应返回各部分的执行结果；任一部分失败时必须明确报错，不能显示为全部成功。

### 6. 手动与自动 Compact

管理界面的“一键压缩”与凌晨自动 Compact 语义完全相同，只是触发方式不同。

两者必须共用同一个入口和完整流程：

1. 生成每日摘要；
2. 审查长期记忆；
3. 执行通过校验的记忆变更批次；
4. 淘汰原始对话；
5. 保存每日摘要；
6. 重建压缩后的上下文；
7. 记录结果。

不能为手动测试保留一套简化逻辑。使用一键压缩应等价于凌晨自动压缩，包括保存长期记忆。

### 7. 已否决方案

#### 模型删除长期记忆

**决定：否决。**

模型可以记和改，但不能删。删除是不可逆且容易受误判影响的操作，只通过管理界面交给用户。

#### 对话中的“忘记”指令

**决定：不支持。**

不为自然语言删除增加识别和确认流程。用户需要删除时直接使用管理界面。

#### 手动 Compact 使用简化测试路径

**决定：否决。**

简化路径无法验证真实凌晨流程。手动与自动触发必须调用同一实现。

## 十二、实现结果

- 长期记忆根目录：`storage.long_term_memory_dir`，默认 `./data/long_term_memory`；
- 用户目录：`SHA-256(user_id)` 前 32 位；
- 限制：索引 200 行/25KB、主题文件 32KB、单用户总量 256KB；
- `memory` 工具：`view`、`create`、`str_replace`；
- 每轮构建上下文时加载 `MEMORY.md`；
- Compact 使用 `<summary>` + `<memory_operations>`，操作要求理由与用户原话证据；
- Compact 文件批次失败不压缩，DB 失败回滚文件，DB 成功后才替换内存；
- 手动和自动 Compact 共用 `_run_compression()`；
- 管理后台支持列表、查看、单条删除；
- 一键清除同时清除对话、每日摘要和长期记忆，保留微信联系人绑定；
- 启动时诊断悬空索引与孤立主题文件；
- 新增文件服务、工具、上下文、Compact 解析/事务和管理 API 测试。
