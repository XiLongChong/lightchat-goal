## 1. 核心设计原则

### 1.1 主动消息是多轮 strict CC 循环，不是"一句了事"

主动回合的正确语义：

```
CALL_LLM
→ wechat_reply("第一句")
→ GUARD_PROACTIVE_OUTPUT → GUARD_OUTPUT → INTERRUPT_CHECK → EXEC
→ APPEND_TOOL_RESULT → POST_SEND_DELAY → INTERRUPT_CHECK
→ CALL_LLM
→ wechat_reply("第二句") 或 done
→ ...
→ done
```

严格 CC 约束不变：
- 禁止 `send_wechat_messages`
- 禁止一次 tool_call 批量发送多条
- 每次 LLM 只能调用一个 tool_call
- 每条可见微信消息都必须由一次 `wechat_reply` 发送
- `wechat_reply` 是 ACTION_TOOL，不是终态
- 发送后回灌 tool result，模型决定继续还是 done
- 最终由 `done` / `skip_proactive` / 最大限制结束

### 1.2 三层判定职责边界

```
┌─────────────────────────────────────────────────────┐
│ 系统前置判定（不调 LLM）                              │
│ 判断现在有没有资格唤醒模型                             │
│ features / 静默期 / 活跃回合 / 频率 / 上限 / 睡眠     │
├─────────────────────────────────────────────────────┤
│ 模型中间判定（LLM 决策）                              │
│ 判断这个主动冲动值不值得说、怎么说、说几句              │
│ 调用 wechat_reply / skip_proactive / done            │
│ 系统不替模型决定表达                                   │
├─────────────────────────────────────────────────────┤
│ 系统后置判定（每次 wechat_reply 前）                   │
│ 判断模型生成的内容能不能真的发出去                      │
│ VALIDATE → GUARD_PROACTIVE → GUARD → INTERRUPT → EXEC│
└─────────────────────────────────────────────────────┘
```

### 1.3 可见上下文一致性（Visible Context Consistency）

**最高优先级不变量。**

定义：模型后续看到的聊天上下文，必须和用户实际看到的聊天内容一致。用户没有收到的 assistant 文本，不能进入后续 LLM 对话上下文。

硬规则：
1. 模型生成过但 guard 拦截的内容，不能写入 conversation history
2. 模型生成过但发送前被用户插话中断的内容，不能写入 conversation history
3. 微信发送失败的内容，不能写入 conversation history
4. 部分发送时，只写确认送达的部分
5. 未确认送达的内容不能进入 `assistant:proactive`
6. 未确认送达的内容不能进入 `recent_proactive_messages.delivered_texts`
7. 未确认送达的内容不能更新 `topic_snapshot` 为"已发生话题"
8. 后续模型不能以为用户看过未送达内容

**分阶段落地（v3.1 修订）：**

- **Phase 4 起**：实现最低限度的 delivered-only 历史写入规则。Phase 4 首次真实发送微信消息，必须从此时起保证：guard RETRY/BLOCK 不写 history、发送失败不写 history、中断不写 history、只有确认送达才写 `assistant:proactive`。
- **Phase 7**：完善完整四态追踪、audit 指标、admin 查询。

不允许 Phase 4-6 存在"已真实发送但历史写入规则还没保证"的空窗期。

职责链：

```
发送层：确认哪些内容真的送达
  ↓
历史写入层：只把确认送达内容写入用户可见聊天历史
  ↓
上下文构造器：只从 confirmed visible history 构造 LLM 上下文
  ↓
日志层：可以记录未发送、被拦截、发送失败内容，但必须与对话历史隔离
```

源头就不要把失败内容写进可见历史，上下文构造器是最后一道防线。

### 1.4 主动回合消息四态 + 三计数器

主动回合内部必须区分四类状态，不混为一个 messages：

| 状态 | 含义 | 写入位置 |
|------|------|----------|
| `attempted` | 模型尝试生成过的文本 | turn audit / dev log / guard log |
| `approved` | guard 通过或清洗后的文本 | turn audit / send attempt log |
| `sent` | 已调用微信发送接口的文本 | send attempt log |
| `delivered` | 微信确认送达的文本 | conversation_history / assistant:proactive / recent_proactive_messages |

只有 `delivered` 能写入用户可见聊天历史和上下文。

**三个独立计数器（v3.1 修订）：**

| 计数器 | 含义 | 用途 |
|--------|------|------|
| `proactive_attempt_count` | 模型尝试生成 `wechat_reply` 的次数 | LLM 行为审计 |
| `proactive_send_attempt_count` | 系统实际调用微信发送接口的次数 | 防故障保护上限 |
| `proactive_delivered_count` | 微信确认送达的消息条数 | allowed_tools 阶段判断主依据 |

**allowed_tools 阶段判断基于 `proactive_delivered_count`，理由：用户没收到，就不能视为"已经说出口"。**

防故障保护：`proactive_send_attempt_count` 另设上限（`hard_max_wechat_reply_per_turn`），防止无限失败重试。`proactive_llm_step_count` 防止 LLM 无限循环。

### 1.5 Guard retry 同回合允许、跨回合禁止

同回合内：guard RETRY 的原因可以回灌给模型修正。

```
你的主动消息包含未经证实的现实观察，例如"我看到你"。
系统没有真实观察依据，请重新调用 wechat_reply，改成自然微信短句。
```

跨回合：guard 拦截的原始文本不能作为 assistant 历史进入上下文。禁止后续模型看到"我刚才说过'我看到你还没睡'"。

#### 2.3 allowed_tools 阶段化（v3.1 修订：基于 delivered_count）

主动回合 allowed_tools 按 **`proactive_delivered_count`** 动态变化：

| 阶段 | 条件 | allowed_tools |
|------|------|---------------|
| A：尚未送达 | `delivered_count == 0` | `[wechat_reply, skip_proactive]` |
| B：已送达，未达上限 | `0 < delivered_count < max_wechat_reply` | `[wechat_reply, done]` |
| C：已达上限 | `delivered_count >= max_wechat_reply` | `[done]` |

阶段化判定在 `_do_call_llm()` 构建 LLMRequest 时执行：

```python
if turn.source == SOURCE_PROACTIVE_IMPULSE:
    delivered = turn.proactive_delivered_count
    max_reply = turn.proactive_meta.get("max_wechat_reply", 3)
    if delivered == 0:
        allowed = ["wechat_reply", "skip_proactive"]
    elif delivered < max_reply:
        allowed = ["wechat_reply", "done"]
    else:
        allowed = ["done"]
```

**关键边界（v3.1 修订）：**

1. 第一条调用微信发送失败，`delivered_count` 仍为 0 → 不进入阶段 B
2. `delivered_count > 0` 后，`skip_proactive` 才语义不成立（Phase 1.6 已保证）
3. 最大限制基于 `delivered_count`；`send_attempt_count` 另设防故障上限
4. 防止无限失败重试：使用 `send_attempt_count` / `llm_step_count`，而非 `delivered_count`

#### 2.4 allowed_tools 双层校验

**第一层：LLM 请求层** — 只暴露当前阶段允许的 tools。

**第二层：后端 classify 层** — `_do_classify_one_tool_call()` 再次校验：

```python
if turn.source == SOURCE_PROACTIVE_IMPULSE:
    if name not in current_allowed_tools:
        turn.add_fallback_event("proactive_disallowed_tool", f"tool={name}")
        return TurnState.PROTOCOL_RETRY
```

校验规则：
- 阶段 A 调用 `done`（未送达就结束）→ `PROTOCOL_RETRY`，要求模型用 `skip_proactive`
- 阶段 B 调用 `skip_proactive`（已送达后跳过）→ `PROTOCOL_RETRY`
- 阶段 C 调用 `wechat_reply`（超限继续发）→ `END_PROACTIVE_MAX_REPLY_LIMIT`
- 主动回合调用 `get_time` / `get_weather` → `PROTOCOL_RETRY`

#### 2.5 主动回合 wechat_reply 限制

**文件**：`agent/chat_agent.py` → `_do_limit_check()`

```python
if turn.source == SOURCE_PROACTIVE_IMPULSE:
    meta = turn.proactive_meta or {}
    max_reply = meta.get("max_wechat_reply", 3)
    # hard_max 兜底：基于 send_attempt_count，防止无限失败重试
    hard_max = self._config.get("proactive", {}).get("turn", {}).get("hard_max_wechat_reply_per_turn", 5)

    max_reply = turn.max_reply_messages_per_turn
```

### Phase 3：主动 guard + 兜底抑制

**目标**：主动消息有专用输出守卫；主动回合失败不发送硬兜底。

#### 3.1 GUARD_PROACTIVE_OUTPUT

**文件**：`agent/output_guard.py`

新增 `guard_proactive_output(text: str) -> tuple[str, str]`：

| 模式 | 处理 | 原因 |
|------|------|------|
| `我看到你` / `我发现你` | RETRY | 编造现实观察 |
| `检测到你` / `监测到` | RETRY | 暴露机制 |
| `系统检测` / `根据数据` | RETRY | 系统味 |
| `提醒你完成` | RETRY | 任务味 |
| `你现在还没睡` / `你今天还没吃饭` | RETRY | 编造观察 |
| `请` + 疑问句 | SANITIZE | 客服味 |
| `请注意休息` | RETRY | 通知味 |

guarded = guard_single_message(text)

```python
class ProactiveScheduler:
    # Phase 4 已有：__init__, is_busy, run_manual_trigger, _execute_proactive_turn

    async def run_heartbeat(self, user_id: str, bot_id: str) -> dict:
        """心跳入口。内部负责锁。"""
        if self._lock.locked():
            return {"status": "skipped", "reason": "active_proactive_turn_running"}
        async with self._lock:
            # 资格检查
            eligible, reason = await self._check_eligibility(user_id, bot_id)
            if not eligible:
                return {"status": "skipped", "reason": reason}
            # 冲动生成（Phase 6 扩展）
            impulse = await self._select_impulse(user_id, bot_id)
            if not impulse:
                return {"status": "skipped", "reason": "no_impulse"}
            # 执行
            self._active_proactive_turn_id = f"heartbeat_{user_id}_{int(time.time()*1000)}"
            try:
                result = await self._execute_proactive_turn(user_id, impulse, bot_id)
                return {"status": "ok", "result": result}
            finally:
                self._active_proactive_turn_id = None
```

## 7. 实施顺序

```
Phase 0  source / proactive_meta 统一               ← 基础契约
  ↓
Phase 1  skip_proactive 独立终态 + 主动专用终态       ← 状态机扩展
  ↓
Phase 2  主动上下文 + allowed_tools 阶段化 + max_llm_steps  ← 模型行为正确
  ↓
Phase 3  主动 guard + 兜底抑制（BLOCK 直接到专用终态） ← 安全边界
  ↓
Phase 4  手动触发 + ProactiveScheduler 最小骨架 + 最低 delivered-only 历史写入  ← 端到端可测
  ↓
Phase 5  scheduler 心跳 + eligibility                ← 自动化基础
  ↓
Phase 6  冲动生成/去重/过期/打分                      ← 完整管道
  ↓
Phase 7  完整四态追踪 + 关系热度 + admin              ← 完整可观测
```

Phase 0-3 改动集中在 `agent/` 内部，不涉及 `main.py`。
Phase 4 首次触达 `main.py` + 新建 `agent/scheduler.py`。
Phase 4 起保证 delivered-only 历史写入，Phase 7 完善四态追踪和审计。
每个 Phase 可独立验收。

### 本阶段做 vs 后移

**本阶段做（Phase 0-7）：**
- 单用户单进程主动消息
- strict CC 工具循环
- 可见上下文一致性（Phase 4 起最低实现，Phase 7 完善）
- 消息四态追踪（Phase 4 起最低 delivered-only，Phase 7 完整）
- 阶段化 allowed_tools（基于 delivered_count）
- 关系热度（简化版）
- 用户回复归因（弱规则版）
- ProactiveScheduler 统一锁管理

**后移：**
- 多用户 / 多 bot / 多实例
- 分布式锁 / 数据库乐观锁
- LLM 驱动的冲动生成（当前用规则）
- 复杂话题切换检测（当前用弱规则）
- 主动消息效果 A/B 测试
- 主动消息个性化策略
