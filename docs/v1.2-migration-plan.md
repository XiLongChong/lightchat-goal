## 1. 当前代码现状摘要

### 1.1 主链路现状

当前主链路已经完成 **v0.2 Phase 1 改造**（commit `46ccf01`），核心结构如下：

```
main.py /chat 端点
  → 构建 system_prompt
  → ChatAgent.chat()
    → TurnScratchpad 初始化（隐式 CREATE_TURN）
    → BUILD_CONTEXT（拼 messages）
    → while state not in TERMINAL_STATES:
      → _dispatch(): CALL_LLM ↔ {HANDLE_MODEL_OUTPUT, CLASSIFY_TOOL_CALLS,
         EXEC_FACT_TOOLS, PROTOCOL_RETRY, TERMINAL_ACTION_BRANCH,
         PARSE_VISIBLE_BATCH, GUARD_OUTPUT, EXEC_SEND_WECHAT,
         SEND_RETRY_UNDELIVERED_ONLY, DECIDE_SEND_TERMINAL,
         EXEC_SKIP_REPLY, HARD_FALLBACK}
    → 返回 TurnResult
  → main.py 手动写历史、写诊断、调 memory_hook、写 draft/turn/diagnostics
```

### 1.2 涉及的关键文件

| 文件 | 职责 |
|---|---|
| `agent/state_machine.py` | `TurnState` 枚举、`TurnScratchpad`、`TurnResult`、`ErrorClass`、`InterruptChecker` |
| `agent/chat_agent.py` | `ChatAgent` 主类，状态机分发 `_dispatch()` + 各 state handler |
| `agent/tool_classifier.py` | `classify_tool_calls()`，工具分类与合法性检查 |
| `agent/tool_registry.py` | `ToolDef` / `ToolRegistry` / 全局 `TOOL_REGISTRY` 注册 |
| `agent/tools.py` | 工具实现（`get_time`, `get_weather`），`execute_tool`, `compute_message_delay` |
| `agent/output_guard.py` | `GUARD_OUTPUT` 全系列（`guard_single_message`, `guard_messages`, `guard_send_message_batch`, `guard_emotion_profanity`） |
| `agent/context_builder.py` | `build_chat_system_prompt`, `compact_history`, `estimate_tokens` |
| `main.py` | FastAPI 路由、历史写入、POST_TURN_HOOKS（分散实现）、诊断记录 |

## 2. 与 v1.2 设计的差距清单

| # | 差距 | 当前表现 | 违反的设计点 | 风险 | 建议处理 |
|---|---|---|---|---|---|
| 1 | `CREATE_TURN（创建回合）` 后无 `INTERRUPT_CHECK（中断检查）` | `TurnScratchpad` 在 `chat()` 开头隐式创建，直接进入 `BUILD_CONTEXT` | v1.2 §5.1 要求 CREATE_TURN 后立刻中断检查 | 用户发了新消息后旧回合继续处理 | `CREATE_TURN` 作为显式状态，进入后立即 INTERRUPT_CHECK |
| 2 | `BUILD_CONTEXT（构建上下文）` 无 `CLASSIFY_CONTEXT_ERROR（上下文错误分类）` | `_do_build_context()` 直接拼 messages 跳到 `CALL_LLM` | v1.2 §6 要求区分 RECOVERABLE/FATAL 错误 | 致命错误（system_prompt 空、工具注册表不可用）未拦截 | 在 BUILD_CONTEXT 内部收集 ContextBuildResult，返回 CLASSIFY_CONTEXT_ERROR 后再决定走向 |
| 3 | 缺少 `OPTIONAL_PREPROCESS（可选预处理）` | `TurnState.OPTIONAL_PREPROCESS` 枚举存在但 `_dispatch()` 无 handler | v1.2 §7 要求在 CALL_LLM 前允许预取事实 | 模型总需额外一轮 tool call 获取时间 | 实现 OPTIONAL_PREPROCESS handler（首版仅预取时间） |
| 4 | `FACT_TOOL（事实工具）` 执行后无 `INTERRUPT_CHECK` | `_do_exec_fact_tools()` 返回 `CALL_LLM`，不检查中断 | v1.2 §5.1 要求长耗时事实工具返回后检查 | 天气查询耗时长，用户可能已发新消息 | 在 EXEC_FACT_TOOLS 返回前 INTERRUPT_CHECK |
| 5 | `FACT_TOOL（事实工具）` 无 `CLASSIFY_TOOL_ERROR（工具错误分类）` | 错误直接作为工具结果回灌模型，不区分可恢复/致命 | v1.2 §10.3 要求区分可恢复/致命错误 | 致命错误（工具执行器不可用）被当做普通结果回灌 | 增加 CLASSIFY_TOOL_ERROR 状态 |
| 6 | `FACT_TOOL（事实工具）` 非真正并行 | `_do_exec_fact_tools()` 用 for 循环串行执行 | v1.2 §10.1 要求多个 FACT_TOOL 并行 | 多个事实工具耗时为累加 | 用 `asyncio.gather()` 并行执行 |
| 7 | `INTERRUPT_CHECK（中断检查）` 位置不全 | 仅 3 处（CALL_LLM 返回后、GUARD_OUTPUT 前、EXEC_SEND_WECHAT 前） | v1.2 §5.1 要求至少 6 处 | 旧回复可能在 HARD_FALLBACK 发送前、CREATE_TURN 后发出 | 补全所有检查点 |
| 8 | `HARD_FALLBACK（硬兜底）` 前无 `INTERRUPT_CHECK` | `_do_hard_fallback()` 直接发送 | v1.2 §14.2 要求兜底发送前中断检查 | 硬兜底发给已被新消息替代的会话 | 在硬兜底发送前加中断检查 |
| 9 | `WRITE_MODEL_HISTORY（写模型用历史）` 在 main.py 中 | 主链路退出的历史写入判断在 `main.py` 的 `if/elif` 中 | v1.2 §15 要求 WRITE_MODEL_HISTORY 在 ChatAgent 内执行 | 终态与历史写入的对应关系靠外部维护，新增终态需改两处 | 在 ChatAgent 内部增加 post-terminal pipeline（见 §4 Phase 5A-5D） |
| 10 | `POST_TURN_HOOKS（回合后钩子）` 在 main.py 中分散 | 记忆提取、诊断记录在 main.py 多处分散调用 | v1.2 §16 要求 POST_TURN_HOOKS 在 ChatAgent 内统一执行 | 钩子逻辑与主链路脱钩 | 通过回调注入，ChatAgent 统一执行 |
| 11 | `WRITE_DEV_LOGS（写开发日志）` 位置不正确 | 诊断分散在 main.py 多处（`record_turn_diagnostics`、`record_usage_event`、`mark_turn_draft_status` 等） | v1.2 §16.3 要求属于 POST_TURN_HOOKS | 开发日志与模型历史混在一起 | 统一收拢到 POST_TURN_HOOKS 回调中 |
| 12 | 送达状态模型不完整 | `wechat_sender` 回调中：异常 → 统一标记 `failed`；无桥 → `failed` | v1.2 §13.3 要求五态送达模型 | 无法区分"发送前失败"和"发送后未知"，前者可安全重试，后者不可 | 五态送达模型 + 重试策略决定（见 §4 Phase 4） |
| 13 | STATE_TOOL 静默 no-op | `_do_exec_state_tools()` 直接返回 CALL_LLM，记录 noop 事件 | v1.2 §11.3 要求 STATE_TOOL 执行后必须 INTERRUPT_CHECK → CLASSIFY_TOOL_ERROR → CALL_LLM | 未来注册 STATE_TOOL 后，未更新此 handler 会静默通过 | 改为：未注册 STATE_TOOL → INVALID_TOOL → PROTOCOL_RETRY；已注册 → 完整流转 |
| 14 | 硬兜底历史标记不规范 | main.py 用 `role="system"` + `[fallback]` 前缀 | v1.2 §14.4：如必须写兜底历史，标记 `assistant:fallback` | system role 的历史条目可能被下游误解 | 改为 `source="assistant:fallback"` 标注 |
| 15 | TurnScratchpad 缺回合元信息字段 | 无 `source`、`input_message_ids`、`interrupt_token`、`status`、`terminal_state` 字段 | v1.2 §4.2 要求 CREATE_TURN 生成这些字段 | 无法跟踪回合完整生命周期 | 扩展 TurnScratchpad |
| 16 | `TurnState` 枚举缺状态 | 当前无 `RECEIVE_EVENT`、`CLASSIFY_CONTEXT_ERROR`、`CLASSIFY_TOOL_ERROR` | v1.2 状态机图 | 无法按设计完整流转 | 增加枚举值 |
| 17 | 无独立 `VisibleMessage` 数据结构 | 消息用 `dict` 裸传递（`{"text": ..., "delay": ..., "send_status": ...}`），无独立 ID | v1.2 §13.2 要求逐条消息独立 ID 和字段 | 无法跨阶段追踪同一消息 | 设计 `VisibleMessage` dataclass |

## 4. 修订后的改造阶段

### Phase 1：状态枚举 + 数据结构整理

**目标**：让 `TurnState` 枚举、`TurnScratchpad` 字段、新增 dataclass 完全对齐 v1.2 设计。

**修改文件**：
- `agent/state_machine.py`

**关键改动**：

1. 在 `TurnState` 枚举中增加：
   ```python
   RECEIVE_EVENT = "receive_event"
   CLASSIFY_CONTEXT_ERROR = "classify_context_error"
   CLASSIFY_TOOL_ERROR = "classify_tool_error"
   ```

2. 扩展 `TurnScratchpad` 字段：
   ```python
   # 回合来源与元信息
   source: str = "user_message"   # TURN_SOURCE
   input_message_ids: list[str] = field(default_factory=list)
   interrupt_token: str = ""      # 由 CREATE_TURN 生成
   status: str = "created"        # created → running → cancelled / ended
   terminal_state: TurnState | None = None
   # context_warnings 用于 CLASSIFY_CONTEXT_ERROR
   context_warnings: list[dict[str, str]] = field(default_factory=list)
   ```

3. 新增 `DeliveryStatus` 枚举（五态送达模型）：
   ```python
   class DeliveryStatus(StrEnum):
       FAILED_BEFORE_SEND = "failed_before_send"    # 发送前失败（可重试）
       UNKNOWN_AFTER_ATTEMPT = "unknown_after_attempt"  # 发送后未知（默认不重试）
       SENT_CONFIRMED = "sent_confirmed"            # 确认已送达
       FAILED_CONFIRMED = "failed_confirmed"        # 确认失败（可重试）
       BLOCKED_BY_GUARD = "blocked_by_guard"        # 被输出保护拦截（不重试）
   ```

4. 新增 `VisibleMessage` dataclass（替代裸 dict）：
   ```python
   @dataclass(slots=True)
   class VisibleMessage:
       visible_message_id: str
       index: int                       # 在 batch 中的序号
       original_text: str               # 模型工具参数中的原始文本
       guarded_text: str = ""           # GUARD_OUTPUT 后的文本
       guard_status: str = ""           # PASSED / SANITIZED / BLOCKED
       delivery_status: str = ""        # DeliveryStatus 值
       attempt_count: int = 0
       wechat_message_id: str = ""      # 微信侧消息 ID
       error_code: str = ""
       delay: float = 0.0
   ```

5. 新增 `ContextBuildResult` dataclass（不放大改造面，仅用于 `_do_build_context` 内部）：
   ```python
   @dataclass(slots=True)
   class ContextBuildResult:
       messages: list[dict[str, Any]]
       warnings: list[dict[str, str]]  # [{"source": "summary_loader", "detail": "..."}, ...]
       fatal_error: str = ""           # 非空表示致命错误
   ```

6. 更新 `TurnResult`：增加 `delivered_messages` 和 `fallback_source` 字段，供外部读取但不做判断。

7. 修改 `InterruptChecker` 签名：从 `() -> bool` 改为 `(interrupt_token: str) -> bool`。

**验收标准**：
- 所有 v1.2 §4.2 要求的字段在 `TurnScratchpad` 中
- `VisibleMessage` 包含 v1.2 §13.2 要求的所有字段
- `DeliveryStatus` 五态完整
- 现有测试全部通过（仅增加类型，不改变行为）

**可能风险**：低。仅增加枚举值、dataclass 和字段，不改流转逻辑。

### Phase 2：Turn Lifecycle 骨架 + 上下文错误分类

**目标**：补全 `RECEIVE_EVENT → CREATE_TURN → INTERRUPT_CHECK → BUILD_CONTEXT → CLASSIFY_CONTEXT_ERROR → OPTIONAL_PREPROCESS` 链路。

**修改文件**：
- `agent/chat_agent.py`（主要）
- `agent/state_machine.py`（配合，已在 Phase 1 改动）

**关键改动**：

1. **`chat()` 方法入口改为从 `RECEIVE_EVENT` 开始**：
   - 在 `chat()` 方法参数中增加 `source: str = "user_message"` 和 `input_message_ids: list[str]`
   - 初始状态从 `TurnState.BUILD_CONTEXT` 改为 `TurnState.RECEIVE_EVENT`
   - `TurnScratchpad` 初始化时设置 `source` 和 `input_message_ids`

2. **增加 `RECEIVE_EVENT` handler**（`_do_receive_event()`）：
   - 将入参信息写入 `TurnScratchpad`
   - 返回 `CREATE_TURN`

3. **增加 `CREATE_TURN` handler**（`_do_create_turn()`）：
   - 生成 `interrupt_token`（`f"it_{turn.turn_id}_{int(time.time()*1000)}"`）
   - 设置 `status = "running"`
   - 返回 `INTERRUPT_CHECK`（`_resume_state=BUILD_CONTEXT`）

4. **`INTERRUPT_CHECK` 改为独立状态**：
   - 在 `_dispatch()` 中增加 `INTERRUPT_CHECK` case
   - handler `_do_interrupt_check(turn, resume_state)`：调用 `_is_interrupted(turn.interrupt_token)`
     - 被中断 → `END_CANCELLED`
     - 有效 → `resume_state`（由上一个状态设置）
   - `TurnScratchpad` 增加 `_resume_state: TurnState` 临时字段

5. **`BUILD_CONTEXT` 返回 `CLASSIFY_CONTEXT_ERROR`**：
   - 修改 `_do_build_context()` 使其返回 `ContextBuildResult`
   - 收集所有可恢复错误到 `context_warnings`
   - 返回 `CLASSIFY_CONTEXT_ERROR`（而非直接 `CALL_LLM`）

6. **增加 `CLASSIFY_CONTEXT_ERROR` handler**（`_do_classify_context_error()`）：
   - 检查 `ContextBuildResult.fatal_error` 是否非空
   - 致命错误 → 设置 `turn.context_warnings`，写事件，→ `HARD_FALLBACK`
   - 无错误 / 可恢复错误 → `OPTIONAL_PREPROCESS`
   - 致命错误清单（v1.2 §6.4）：
     - `missing_user_message`
     - `system_prompt_build`（当前检查：`_do_build_context` 中 system_prompt 为空时使用默认 prompt，属于降级，不致命）
     - `tool_registry_unavailable`（TOOL_REGISTRY 为空 → FATAL）
     - `tool_schema_validation`（_build_native_tool_specs 返回 None → FATAL）
     - `send_wechat_messages_schema_missing`
     - `skip_reply_schema_missing`

7. **实现 `OPTIONAL_PREPROCESS` handler**（`_do_optional_preprocess()`）：
   - 预取当前时间（调用 `_get_time` 或直接格式化 `datetime.now()`）
   - 将结果作为 system 消息注入 `turn.messages`
   - **不预取天气**（首版只预取时间）
   - 始终返回 `CALL_LLM`
   - 预取失败 → 记录 warning，仍返回 `CALL_LLM`

**验收标准**：
- `CREATE_TURN` 是显式状态，进入后立即 `INTERRUPT_CHECK`
- `BUILD_CONTEXT` 后必须 `CLASSIFY_CONTEXT_ERROR`
- 致命上下文错误 → `HARD_FALLBACK`
- 可恢复错误降级继续，`context_warnings` 被记录
- `OPTIONAL_PREPROCESS` 注入时间信息，不生成回复
- 现有测试全部通过

**可能风险**：中。上下文构建链路改动较大，`_do_build_context` 需重构为返回 `ContextBuildResult`。但改为在 handler 内部构建 `ContextBuildResult`，不扩大改造面到 `context_builder.py`。

### Phase 3：模型输出协议 + 工具分类 + 并行事实工具 + 工具错误分类

**目标**：实现 FACT_TOOL 并行执行、CLASSIFY_TOOL_ERROR、STATE_TOOL 严格模式、INTERRUPT_CHECK 补全。

**修改文件**：
- `agent/chat_agent.py`（主要）

**关键改动**：

1. **`FACT_TOOL` 并行执行**：
   - 当前串行 for 循环改为 `asyncio.gather(*tasks)`
   - 每个工具独立 try/except，单个失败不影响其他
   - 结果按原始 tool_calls 顺序合并 → 回灌 `turn.messages`
   - 执行后 → `INTERRUPT_CHECK`（`_resume_state=CLASSIFY_TOOL_ERROR`）

2. **增加 `CLASSIFY_TOOL_ERROR` handler**（`_do_classify_tool_error()`）：
   - 遍历所有事实工具执行结果
   - 分类规则：
     - 全部成功 → `CALL_LLM`
     - 有可恢复失败（如 weather timeout、time failed）→ 将失败结果作为 tool result 回灌 → `CALL_LLM`
     - 致命失败（如 `tool_registry_corrupted`、`tool_executor_unavailable`）→ `HARD_FALLBACK`
     - `invalid_tool_args` → `PROTOCOL_RETRY`

3. **STATE_TOOL 改为严格模式**：
   - 当前 `_do_exec_state_tools()` 直接返回 `CALL_LLM`
   - 改为：
     - 如果 TOOL_REGISTRY 中无任何 `tool_category="state_tool"` 的注册 → 此状态不应到达（CLASSIFY_TOOL_CALLS 会先将其归为 unknown → PROTOCOL_RETRY）
     - 未来有注册时：执行 → `INTERRUPT_CHECK` → `CLASSIFY_TOOL_ERROR` → `CALL_LLM`
     - 不再记录 noop 事件；未实现的 STATE_TOOL 不会静默成功

4. **补全 INTERRUPT_CHECK 位置**（共 6 处，在各自 handler 内调用或进入独立 INTERRUPT_CHECK 状态）：
   - `CREATE_TURN` 后（Phase 2 已实现）
   - `CALL_LLM` 返回后（当前 `_do_handle_model_output` 中已有）
   - `EXEC_FACT_TOOLS` 返回后（本 Phase 增加）
   - `EXEC_STATE_TOOLS` 返回后（本 Phase 编译器保留调用）
   - `GUARD_OUTPUT` 前（当前已有）
   - `EXEC_SEND_WECHAT` 前（当前已有）
   - `HARD_FALLBACK` 发送前（本 Phase 增加）

5. **HARD_FALLBACK 增加 INTERRUPT_CHECK**：
   - 在 `_do_hard_fallback()` 开头增加中断检查
   - 被中断 → `END_CANCELLED`

6. **interrupt_token 生成机制**：
   - `ChatAgent` 内部维护 `_active_interrupt_token: str`
   - `CREATE_TURN` 时设置
   - `_is_interrupted()` 检查: 如果外部 checker 注入 → `checker(self._active_interrupt_token)`；如果未注入 → 记录一次 warning → 返回 False（防御性默认）
   - 在 `ChatAgent.__init__` 中增加 `always_false_checker`：`set_interrupt_checker` 未被调用时，如果是 `test_mode=True` → 使用 `always_false`；如果是生产模式 → 不设 checker 会导致 warning，但不崩溃

**验收标准**：
- 多个 FACT_TOOL 并行执行，耗时 ≤ 最慢单个工具
- 单个工具失败不中断其他工具
- 工具错误正确分类（可恢复/致命/协议错误）
- STATE_TOOL 不再静默 no-op
- HARD_FALLBACK 发送前检查中断
- 所有 6 处 INTERRUPT_CHECK 就位
- 现有测试全部通过

### Phase 4：发送链路 — VisibleMessage + 五态送达模型 + 逐条重试

**目标**：发送链路使用 `VisibleMessage` 替代裸 dict；送达状态改为五态模型；重试策略与五态对齐。

**修改文件**：
- `agent/chat_agent.py`（主要）
- `agent/state_machine.py`（配合 — VisibleMessage 在本文件定义）
- `main.py`（wechat_sender 回调适配五态模型）

**关键改动**：

1. **`PARSE_VISIBLE_BATCH` 中创建 `VisibleMessage`**：
   - 解析后为每条消息分配 `visible_message_id`（`f"vm_{turn_id}_{index}"`）
   - 创建 `VisibleMessage(visible_message_id=..., index=i, original_text=raw_text)`
   - 存入 `turn.visible_messages: list[VisibleMessage]`（取代 `turn.visible_batch: list[str]`）

2. **`GUARD_OUTPUT` 适配 `VisibleMessage`**：
   - 从 `turn.visible_messages` 读取 `original_text`
   - guard 后写入 `guarded_text` 和 `guard_status`（`PASSED`/`SANITIZED`/`BLOCKED`）
   - BLOCKED 的消息设置 `delivery_status = DeliveryStatus.BLOCKED_BY_GUARD`
   - 通过的消息继续

3. **`EXEC_SEND_WECHAT` 适配五态送达模型**：
   - 发送前：未发送的消息 `delivery_status = ""`
   - 发送后 `wechat_sender` 回调返回时，逐条设置 `delivery_status`：
     - `_bridge is None` / no token → `FAILED_BEFORE_SEND`
     - 调用成功（`send_text` 未抛异常）→ `SENT_CONFIRMED`
     - 调用抛出异常且能确认未发送 → `FAILED_BEFORE_SEND`
     - 调用抛出异常但无法确认是否发送（如超时、连接断开）→ `UNKNOWN_AFTER_ATTEMPT`

4. **五态送达模型定义**：
   | 状态 | 可重试 | 写成功历史 |
   |---|---|---|
   | `FAILED_BEFORE_SEND` | 是 | 否 |
   | `UNKNOWN_AFTER_ATTEMPT` | **否**（默认） | 否 |
   | `SENT_CONFIRMED` | 否 | 是 |
   | `FAILED_CONFIRMED` | 是 | 否 |
   | `BLOCKED_BY_GUARD` | 否 | 否 |

5. **`SEND_RETRY_UNDELIVERED_ONLY` 适配五态**：
   - 只重试 `FAILED_BEFORE_SEND` 和 `FAILED_CONFIRMED`
   - 不重试 `UNKNOWN_AFTER_ATTEMPT`（避免重复发送）
   - 不重试 `SENT_CONFIRMED`
   - 不重试 `BLOCKED_BY_GUARD`

6. **`DECIDE_SEND_TERMINAL` 适配五态**：
   - 至少一条 `SENT_CONFIRMED` 且全部为 `SENT_CONFIRMED` → `END_SENT`
   - 至少一条 `SENT_CONFIRMED` 且存在非 `SENT_CONFIRMED` → `END_PARTIAL_SENT`
   - 无 `SENT_CONFIRMED` → `END_FAILED`

7. **`main.py` `wechat_sender` 回调适配**：
   - 当前所有异常统一标记 `failed`
   - 改为区分：
     - 如果 `send_text` 调用成功（未抛异常）→ `SENT_CONFIRMED`
     - 如果抛异常 → 根据异常类型判断：连接/超时类 → `UNKNOWN_AFTER_ATTEMPT`；参数/认证类 → `FAILED_BEFORE_SEND`
   - 保守策略：无法确认的异常默认为 `UNKNOWN_AFTER_ATTEMPT`

8. **`TurnResult` 中的 `visible_messages`**：
   - 从 `list[dict]` 改为 `list[VisibleMessage]`（或序列化后的 dict）
   - `delivered_count` 属性改为统计 `delivery_status == SENT_CONFIRMED`

**验收标准**：
- 每条消息有独立 `visible_message_id`
- `GUARD_OUTPUT` 后的消息 `guarded_text` 和 `guard_status` 正确设置
- `SEND_RETRY` 只重试 `FAILED_BEFORE_SEND` 和 `FAILED_CONFIRMED`
- `UNKNOWN_AFTER_ATTEMPT` 不重试、不写成功历史
- `SENT_CONFIRMED` 消息绝对不重试
- 全部 `SENT_CONFIRMED` → `END_SENT`
- 部分 `SENT_CONFIRMED` → `END_PARTIAL_SENT`
- 无 `SENT_CONFIRMED` → `END_FAILED`
- `BLOCKED_BY_GUARD` → 全部被拦截 → `HARD_FALLBACK`

**可能风险**：中。`VisibleMessage` 替代裸 dict 涉及多处数据流改动（`visible_batch` → `guarded_batch` → `sent_results`）。`wechat_sender` 回调的异常分类需要在实际微信 iLink 上调试验证。

## 8. 仍需用户确认的问题

### Q1：interrupt_token 的 checker 注入时机

`ChatAgent` 在 `__init__` 时可能还没有 checker（因为 `main.py` 的 checker 可能依赖请求上下文如 `user_id`）。需要在每次 `chat()` 调用时动态注入。

**方案 A**：`ChatAgent.chat()` 方法接受 `interrupt_checker: InterruptChecker | None = None` 参数，每次调用时传入。

**方案 B**：`ChatAgent.set_interrupt_checker()` 在每次 `chat()` 调用前设置（当前已有此方法）。

**建议**：方案 A（每次 chat 调用时传入），因为 checker 会依赖当前请求的 `user_id`（检查该用户是否有新消息），是请求级别的状态，不应是 ChatAgent 实例级别。但需注意 checker 现在是 `(token: str) -> bool` 而非 `() -> bool`。

### Q2：`wechat_sender` 回调的异常分类

当前 `wechat_sender` 中 `_bridge.send_text()` 抛异常时，需区分是"发送前失败"还是"发送后超时"。`httpx` 等库通常按异常类型区分：连接错误、超时 → 可能未发送（UNKNOWN）；认证/参数错误 → 确认未发送（FAILED_BEFORE_SEND）。

**方案 A**：保守策略——所有 `send_text` 异常默认标记 `UNKNOWN_AFTER_ATTEMPT`，不自动重试。

**方案 B**：精细分类——根据异常类型区分。

**建议**：方案 A（保守），因为微信 iLink 的 `send_text` 返回时我们无法确认消息是否已被微信服务器接收。默认不重试最安全。发不出去比发两次好。

### Q3：Phase 5C 兼容开关的配置方式

需要在 `config.yaml` 中增加 `features.post_terminal_in_agent` 开关。是否接受在 `config.yaml` 中新增字段？

当前的 `features` 配置段已有 `memory` 等字段，新增一个 `post_terminal_in_agent` 与现有结构一致。
